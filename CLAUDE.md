## What this is

ZeroStockView (在庫状況調査システム) is an internal inventory-survey tool. A user uploads three warehouse stock-report files; Amazon's own/FBA stock is instead synced from Amazon's SP-API. The app matches the rows against a configured set of product codes (品番) and stores a snapshot of per-SKU stock levels by warehouse. That snapshot is called a "survey" (調査). Surveys can be viewed, annotated with memos, exported to Excel, charted over time, and read by an external partner through a rate-limited public API. Domain requirements and sample input/output files are in `doc/` (in Japanese). Read `doc/要件概要.md` / `doc/要件定義書.md` before changing import rules, `doc/Amazon在庫と在庫調査の統合改修計画.md` before touching Amazon stock sync, and `doc/外部公開API仕様書.md` before changing the external API.

## Architecture

**SPA served by Laravel.** `routes/web.php` defines every JSON endpoint under the `/api` prefix (session auth through the `auth` middleware; there is no `routes/api.php`). A final catch-all `Route::view('/{any}', 'app')` hands everything else to the Vue app. Auth uses Laravel session cookies plus a CSRF token, which `resources/js/app.ts` reads from a meta tag and sets on axios. Users log in with `login_id`, not email.

**Import pipeline** (`app/Services/InventoryImportService.php`) is the core of the app:
1. An `ImportSetting` (named; 1–50 `ImportTarget` product codes) selects which products to survey.
2. `CrossWalkerClient` refreshes those products and their SKUs (ASIN, TQ item/color/size) from the external product-identifier API ("CrossWalker", configured via `CROSSWALKER_*` in `config/services.php`). API failures throw `CrossWalkerException`, which renders as a JSON error response.
3. Three uploaded files are parsed, each keyed by an internal name with a Japanese display type (`FILE_TYPES`): BOSS (one CSV supplying both own-warehouse and RFC stock), TQ KEEP list → `ec_stock` (summed per SKU), and TQ stock inquiry → `free_stock`. Rows are matched to SKUs by SKU code or the TQ item/color/size key. Amazon own/FBA stock is *not* uploaded — see "Amazon inventory sync" below.
4. Inside one transaction, `Product`/`Sku` master data is copied into `Survey` → `SurveyProduct` → `SurveySku` snapshot rows with the stock columns (Amazon columns start `NULL`, meaning "取込待ち"). The uploaded files are stored on the `local` disk as `SurveyFile` records with a 30-day `expires_at`.
5. `reimport` ("rerun") replays a past survey's stored files against a different setting while keeping the original `executed_at`. It fails once the files have expired.
6. `import()` calls `SurveyAmazonInventorySyncService::syncSurvey` twice — once inside the creation transaction, once again right after it commits (to catch an Amazon import that finished mid-transaction) — so a freshly-created survey picks up that Tokyo calendar day's Amazon stock immediately if it already arrived. The second call is best-effort: failures are logged, not thrown, since the survey itself already saved successfully.

The `Product`/`Sku` tables are a cache of CrossWalker master data. `survey_*` tables are denormalized snapshots, so history stays stable when master data changes. Expired files are pruned by the scheduled `survey-files:prune` command (`routes/console.php`) and also opportunistically in `SurveyController::index`.

**Amazon inventory sync** is a separate pipeline from the file-based import above, added to replace manually-uploaded Amazon reports with Amazon's SP-API:
- `amazon-inventory:queue` runs daily at 09:00 JST (`routes/console.php`) and enqueues one `AmazonInventoryImport` row (`AmazonInventoryImportService::queue`); only one can be `queued`/`running` at a time (enforced by a DB unique constraint on `active_key`). A `queue:work amazon_inventory` worker (the `amazon_inventory` connection and `amazon-inventory` queue, see `config/queue.php`) picks it up every 5 minutes and runs `AmazonInventoryImportService::process`, which calls `AmazonReportClient` to fetch both SP-API reports (`GET_FLAT_FILE_OPEN_LISTINGS_DATA`, `GET_FBA_MYI_UNSUPPRESSED_INVENTORY_DATA`, configured via `amazon_sp_api.*` in `config/services.php`), matches rows to the currently-tracked SKUs, and writes one `AmazonInventorySnapshot` per SKU plus a `snapshot_date` (the Tokyo calendar day the data is "as of").
- `SurveyAmazonInventorySyncService::syncSurvey` copies the *latest successful* same-day import's snapshot onto a survey's `SurveySku.amazon_own_stock`/`amazon_fba_stock` (by `sku_code`) and records the applied import on `Survey.amazon_inventory_import_id`. It only touches surveys with `Survey::AMAZON_SOURCE_SP_API` (the new 3-file kind); legacy 5-file surveys (`AMAZON_SOURCE_LEGACY_FILE`) keep whatever Amazon numbers they were imported with and are never overwritten. A SKU with no matching snapshot stays `NULL` ("未取得／対象外"), not 0 — downstream totals must treat `NULL` as "pending", never as zero stock. When an `AmazonInventoryImport` succeeds, `process()` also calls `syncDate($import->snapshot_date)` to retroactively backfill every already-created survey for that Tokyo day, not just future ones.
- `Schedule::call(...->expireStale())` runs every 5 minutes and fails any `AmazonInventoryImport` stuck `running`/`queued` past its timeout. `SurveyAmazonInventorySyncService::syncPendingDate` lets a once-missed day's survey catch up once an import for that day succeeds; `php artisan survey:amazon-audit` (`AuditSurveyAmazonInventory`, read-only) classifies every historical survey into `three_file`/`legacy_file`/`ambiguous` via `SurveyAmazonInventoryClassifier` and was used for the legacy→SP-API migration — don't repurpose its classification logic without reading `doc/Amazon在庫と在庫調査の統合改修計画.md` first, the rules around what counts as "ambiguous" are deliberate.

**Outputs.** `SurveyExcelExporter` writes `.xlsx` by hand (raw OOXML zipped). No spreadsheet library is installed, so keep it that way unless asked. Inventory trends (`InventoryTrendController`, `InventoryTrendCsvExporter`) aggregate `survey_skus` across surveys by date; they are not a separate data store.

**API shape.** Responses are built with API Resources or arrays that emit camelCase keys and string IDs (e.g. `SurveyResource`). TypeScript types in `resources/js/types/index.ts` and `resources/js/api/*.ts` mirror these shapes, so update both sides together.

**External public API.** `GET /api/v1/inventory/daily` (`ExternalInventoryController::daily`, see `doc/外部公開API仕様書.md`) is the one endpoint outside the session-auth SPA — it's gated by the `inventory.api` middleware (`AuthenticateInventoryApi`), not Laravel's session `auth`. Callers send an `X-API-Key` header checked against the single `ApiConnectionSetting` row (key stored only as a SHA-256 hash; `ApiConnectionSettingController::rotateKey` is the only place the plaintext key is ever shown) and their source IP against that setting's `allowed_networks` (CIDR list, matched by `IpNetworkMatcher`). It's also rate-limited (`throttle:60,1`) and returns the same `survey_skus`-derived rows as `InventoryTrendCsvExporter`, so it must stay consistent with the in-app trend view and CSV export.

**Frontend.** Vue 3 + Pinia (with `pinia-plugin-persistedstate`) + Vue Router + Tailwind v4/Flowbite. Pages are lazy-loaded in `resources/js/router/index.ts`. The router guard calls `auth.initialize()` (`GET /api/user`) and redirects unauthenticated users unless the route has `meta.public`. `app.ts` mounts the app first and preloads the import-settings and surveys stores behind a global loading indicator (`router/loading.ts`). Shared UI primitives are the `Base*` components in `components/ui/`; reuse them. The `@` alias resolves to `resources/js`. Vitest tests mock `vue-router` and the `@/api/*` modules with `vi.mock`, and backend tests fake CrossWalker with `Http::fake`.

UI text, validation messages, and comments are in Japanese. Match that.
