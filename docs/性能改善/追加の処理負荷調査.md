# 追加の処理負荷調査

調査日: 2026-10-20。コードを確認し、設定先DBを読み取り専用で計測した。処理の変更や取込の実行はしていない。ログイン時の全履歴明細取得は [調査履歴の全件明細読込を解消.md](./調査履歴の全件明細読込を解消.md) に記載済み。

## 優先して改善する候補

### 1. CrossWalker同期でSKUマスタを毎回全件削除・再登録する

`src/app/Services/CrossWalkerClient.php` の `refresh()` は対象品番を取得した後、各品番の `syncProduct()` を呼ぶ。`syncProduct()` は取得内容が前回と同じでも、品番を保存し、その品番のSKUをすべて削除して再登録する。この同期はファイル取込、Amazon在庫取込、品番グループ保存から実行される。

調査時点の対象は重複除去後112品番、直近調査のSKUは817件。対象が変わらない取込でも、CrossWalkerが返した対象SKUの件数分、削除と再登録が発生する。品番ごとのUPDATEとモデル生成も伴う。マスタにある削除対象SKUの正確な件数と、取込処理の経過時間やDB待機時間への寄与は未計測。

**修正案:** CrossWalkerから取得した品番・SKUを既存行と比較し、変更された行だけ更新し、追加・削除分だけ反映する。SKUのIDを維持できる設計にする。品番の状態、並び順、ASIN、TQの対応情報、CrossWalker側で消えたSKUの扱いを含めて検証する。外部APIへの品番照会自体は最新情報が必要なため、この修正だけではなくならない。

### 2. 同日の再取込で調査品番・SKUを全件作り直す

`src/app/Services/InventoryImportService.php` の `writeProducts()` は既存のメモと所属を読み取った後、当日の調査品番を全件削除し、対象品番とSKUを全件作成する。1ファイルの追加取込や再照合でも呼ばれる。調査時点の直近調査は112品番・817 SKUで、更新対象が一部でも同規模の書込みが繰り返される。DB書込み量、トランザクション時間、行IDの変更に影響する。実行時間は未計測。

**修正案:** 品番コード・SKUコードをキーにして既存行を更新し、追加・削除分だけ処理する。メモ、グループ所属、未確定在庫の `null` と確定値、古いSKUの削除、並び順の更新を従来どおり維持する。現行APIが調査品番・SKUのIDを返すため、IDの安定性もテストする。

## 次に確認する候補

### 3. 取込CSVを複数回丸ごとメモリに読み込む

`InventoryImportService.php` の `classifyFiles()` は種類判定のため各ファイル全体を読み込み、`rows()` は同じファイル全体を再度読み込んで全行の配列を作る。入力は最大3ファイル、各20 MiBまで許可される。大きいファイルでは、文字列と行配列を同時に持つためPHPメモリの使用量が増える。実ファイルでのピークメモリは未計測。

**修正案:** 種類判定では先頭行だけ読み、取込本体はストリームから順次行を処理する。文字コード変換、重複チェック、行番号付きエラーを維持する。

### 4. 調査保存後にAmazon在庫をもう一度照合する

`InventoryImportService.php` は調査の保存中とコミット後に `syncSurvey()` を呼ぶ。後者は、コミットと並行してAmazon在庫取込が完了する競合を拾うために必要な処理である。一方、新しいAmazon取込がない場合も `SurveyAmazonInventorySyncService.php` がスナップショットと調査の全SKUを再読込・走査する。

**修正案:** コミット後に最新の成功取込IDを比較し、保存中に適用済みの取込から変わっていない場合だけ全SKU照合を省く。並行完了を再現するテストを先に作る。単純に2回目の呼出しを削除しない。

### 5. 在庫履歴の全品番出力を一度に配列化する

`InventoryTrendCsvExporter.php` の `rows()` は対象期間の調査、調査SKU、Amazonスナップショットを読み込み、全日・全品番の行配列を作る。CSV出力もこの配列を経由し、外部日次APIは配列をそのままJSONで返す。期間上限は365日。調査時点の全品番・2026-09-01～2026-10-20の読み取り専用CLI計測では、3,977行、行生成約1.13秒、JSON約0.85 MB、PHPピークメモリ44 MBだった。現在のデータ量では緊急性は低いが、日数とSKU数に比例して増える。

**修正案:** CSVは日付単位などで順次書き出す。外部APIは応答仕様を維持する必要があるため、上限やページングを別途検討する。まず実運用の最大期間と応答時間を測る。

## 優先度が低い候補

- `SurveyResultPage.vue` はSP-API調査の結果画面を開いている間、状態が完了していても30秒ごとに `GET /api/surveys/{id}` で選択中の調査の全明細を取得する。開いているタブが増えるほど通信とJSON生成が増える。画面非表示時の停止や更新条件の絞込みを検討する。ただしAmazon取込完了後の自動反映は維持する。
- `SurveyController.php` の履歴一覧GETは期限切れファイルを毎回検索・削除するが、同じ整理を日次スケジュールでも行う。`AmazonInventoryImportController.php` の一覧・詳細GETでも、5分ごとのスケジュールと同じ期限切れ取込の更新を実行する。スケジューラーの運用が確認できれば、閲覧リクエストから整理処理を外す余地がある。
- 取込画面とサイドバーの連携表示は、それぞれAmazon取込一覧を取得する。取込画面は処理中に5秒間隔、サイドバーは5分間隔。応答は最大50件なので影響は小さい。

## 判断と計測上の注意

現時点で最も直接的に品番・SKU増加の影響を受けるのは、マスタ同期と調査の全件再作成。100品番を超えたことだけを理由に直ちに障害になる根拠はない。次に改善するなら、まずこの2経路で取込時間、SQL発行数、DB待機時間、PHPピークメモリを計測する。上記の削除・再登録件数はコードと現在の件数からの推定であり、本番の所要時間を測った値ではない。
