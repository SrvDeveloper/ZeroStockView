# 調査履歴の全件明細読込を解消する

## 現状と問題

ログイン成功直後に `LoginPage.vue` が `surveys.load()` を呼ぶ。ログイン済みでページを開き直した場合も `app.ts` が同じ処理を呼ぶ。`surveys.load()` の `GET /api/surveys` は、全調査の `products.skus` とファイル情報をページングせずに取得し、`SurveyResource` が各SKUの在庫数・メモまで返す。このため、調査履歴や在庫調査結果を開かなくても、過去の全SKU明細がブラウザーへ送られる。

2026-10-20にワークスペースの設定先MySQLを読み取り専用で調べた時点では、調査23件、保存済みの調査SKUは計5,911件だった。Laravel CLIで一覧APIと同じ関連データの読込みと `SurveyResource` のJSON生成を3回測った結果は、合計2.3～3.2秒、JSON約1.85 MB、PHPのピークメモリ48 MBだった。認証・期限切れファイルの整理・HTTP通信・ブラウザー描画はこの測定に含まない。直近の調査だけでも112品番・817 SKUがあり、履歴の蓄積に伴って初期読込量が増える。

品番数100件は実装上の上限でも、この問題の発生条件でもない。改善対象は、ログイン時に全履歴のSKU明細を取得する処理である。

## 修正方針

1. `GET /api/surveys` を履歴一覧用の軽い応答にする。日付、ID、Amazon取込状態と基準日時、品番数・SKU数、全倉庫ゼロ・一部ゼロ件数、保存ファイルの状態など、一覧・カレンダー・ファイル管理・連携ステータスに必要な項目を返す。SKU別在庫数やメモは含めない。
2. 一覧の集計値を作るために、全調査のSKUモデルを読み込んでから捨てる実装にはしない。集計クエリまたは保存済み集計値を使い、`null`（未確定）と確定した0、Amazon対象外の判定を既存の `summarizeSurvey()` と一致させる。
3. `GET /api/surveys/{id}` は選択した調査の明細取得に使う。結果画面を直接開いた場合にも明細を取得し、前回比の表示には直前調査の集計値を使用する。Amazon取得後の30秒ごとの再読込と手動再読込は、表示中の調査だけを更新する。
4. フロントエンドのストアで「履歴一覧の概要」と「取得済みの調査明細」を分ける。取込・再照合・メモ変更・調査削除・ファイル削除の後は、表示中の明細と一覧の概要を矛盾なく更新する。
5. 一覧の件数がさらに増える場合は、日付範囲またはページングで概要の取得範囲を絞る。カレンダーの月移動、リストの期間検索、直前調査との比較に必要なデータを取得できる設計にする。

## 完了条件

- ログイン直後とログイン済みでの再表示時に、過去の全SKU明細を取得しない。`GET /api/surveys` のDB処理・応答に全件の `products.skus` が含まれない。
- 履歴のカレンダーとリストで、調査日、件数、Amazon状態、前回比、ファイル状態、ダウンロード・Excel出力・削除が従来どおり動く。集計値は変更前の結果と一致する。
- 結果画面を履歴から開いてもURLを直接開いても、その調査の全SKU明細、メモ、グループ絞込、Excel出力、再照合を表示できる。前回比とAmazon反映後の再読込も一致する。
- 閲覧者・編集者・特権管理者の表示と操作権限が変わらない。既存の公開外部APIの応答は変えない。
- 変更前後で同じデータを使い、初期読込の応答サイズ、サーバー処理時間、PHPメモリ、ブラウザーの表示時間を測定して記録する。履歴が増えた条件でも確認する。
- PHPUnitとVitestで一覧の集計、明細の遅延取得、直接URL、更新後の整合性を確認し、`composer test`、`npm run check`、`npm run build` を通す。
