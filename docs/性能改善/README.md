# 性能改善

システムの処理負荷と無駄を減らすための調査結果とチケット。チケット番号は `PERF-xx` で管理する。

## 調査結果

- [調査履歴の全件明細読込を解消.md](./調査履歴の全件明細読込を解消.md)（Codex）: ログイン時に全調査の全SKU明細を取得している問題と修正方針。
- [追加の処理負荷調査.md](./追加の処理負荷調査.md)（Codex）: CrossWalker同期、同日再取込、CSV読込、コミット後の再照合、在庫推移の出力など。
- [Claudeによる追加調査.md](./Claudeによる追加調査.md)（Claude）: アイコンフォント、応答の未使用項目、Amazon在庫の1行ずつの更新、和文フォント、結果画面の再描画など。Codexの修正案への補足も含む。

以下、チケットの「出典」は、C＝Codex（調査履歴＝`調査履歴の全件明細読込を解消.md`、追加＝`追加の処理負荷調査.md` の番号）、Cl＝Claude（`Claudeによる追加調査.md` の番号）。

## 進め方

1. **すぐ効くもの（PERF-01〜02）:** 変更が小さく、初回表示と通信量に効く。
2. **調査履歴と結果画面（PERF-03〜04）:** ログイン時の全明細取得をやめる。画面とAPIの両方を変える。
3. **取込経路（PERF-05〜08）:** 先に計測（PERF-05）してから、同期と書込みを差分にする。
4. **個別の改善（PERF-09〜11）:** 単独で進められる。
5. **判断が必要なもの（PERF-12〜13）:** 見た目や運用の方針を決めてから進める。

### PERF-06 CrossWalker同期を差分更新にする

出典: C追加1、Cl（Codexの修正案への補足）。

- `追加の処理負荷調査.md` の1の修正案のとおり。取得した品番・SKUを既存行と比べ、変わった行だけ更新し、追加・削除分だけ反映する。
- SKUマスタの一意制約（`child_asin`、`tq_item_no`・`tq_color_no`・`tq_size` の組）に注意する。2つのSKUの値が入れ替わるケースを先にテストにする。
- 完了条件: PERF-05と同じ方法で、変更前後のSQL発行数と所要時間を記録する。

**実装状況（2026-10-20）:** 実装済み。`CrossWalkerClient::syncProducts()` で、対象の全品番をまとめて比べ、中身が変わった品番だけを保存する（変わらない品番は同期日時だけを1文で更新）。SKUは「なくなった・変わったSKUを消す」→「新しい・変わったSKUをまとめて入れる」の順にするので、一意制約のある値が品番をまたいで入れ替わっても途中で重ならない。SKUのIDはほかの表から参照されていないので、変わったSKUは入れ直す。取込・Amazon在庫取込・品番グループの保存のすべてで使う。

- 品番グループに入っていない品番が持っているASIN・SKUと重なる場合は、変更前と同じく一意制約で失敗する（今回の対象外）。

### PERF-07 調査の品番・SKUを差分更新し、Amazon在庫を作成時に入れる

出典: C追加2、C追加4、Cl-3。

- `writeProducts()` を、品番コード・SKUコードをキーにした差分更新にする（`追加の処理負荷調査.md` の2の修正案）。
- 調査SKUを作るとき、その日の最新の成功取込のAmazon在庫を最初から入れる。`syncSurvey()` は差分がなければ書き込まず、書き込むときもまとめて更新する。Amazon取込の成功時の反映（`syncDate()`）も同様にする。
- コミット後の再照合は、適用済みの取込から変わっていなければ省く（`追加の処理負荷調査.md` の4の修正案）。並行して取込が完了する競合のテストを先に作る。
- メモ、グループ所属、未確定（`null`）と確定値、ASINのないSKU、古いSKUの削除、並び順、IDの扱いを現行どおりにする。

**実装状況（2026-10-20）:** 実装済み。

- `InventoryImportService::writeProducts()` は、調査品番を品番コード、調査SKUを「品番コード＋SKUコード」で既存行と突き合わせ、なくなった行を消す → 値の変わった行をまとめて更新 → 新しい行をまとめて追加する。変わらない行は書かない。行のIDとメモは残る。別の品番へ移ったSKUは入れ直し、メモはSKUコードで引き継ぐ（変更前と同じ）。まとめて書く処理は `BulkRowWriter`（`列 = CASE id WHEN … END` の UPDATE と複数行 INSERT）。
- 並び順には一意制約があり、MySQL も SQLite も1行ずつ確かめるので、並び順が変わる行は先に重ならない値へ退避してから書く（退避を外すと `SurveyDifferentialWriteTest` の並べ替えのテストが一意制約で落ちることを確かめた）。
- 調査SKUを書くときに、その日の最新の成功取込のAmazon在庫（とASINのないSKUへのASINの補完）を最初から入れ、調査の `amazon_inventory_import_id` も同時に設定する。ファイル取込・Amazon在庫取込からの調査作成の両方。補完の規則は `SurveyAmazonInventorySyncService::amazonValues()` にまとめ、`syncSurvey()` と共通にした。
- `syncSurvey()`（`syncDate()`・`syncPendingDate()` から呼ばれる）は、変わった行だけをまとめて更新する。
- 保存後の再同期は `syncSurveyIfNewerImport()` にし、反映済みの取込より新しい成功取込があるときだけ行う。保存中に取込が完了する競合は、`ApiBackendTest` のテストをトランザクションのコミット時に取込を完了させる形に書き直して確かめている（保存後の再同期を外すと落ちる）。

| 計測（PERF-05の計測用テスト、3回の中央値） | 所要時間（PERF-06後→後） | SQL（PERF-06後→後） | トランザクション（PERF-06後→後） |
| --- | --- | --- | --- |
| Amazon在庫取込（調査を新規作成） | 2,436 → 1,108 ms | 2,081 → 593 | 2,224 → 889 ms |
| 取込（3ファイル、Amazon在庫あり） | 2,471 → 1,025 ms | 1,522 → 37 | 2,136 → 686 ms |
| 同日の追加取込（1ファイル） | 2,452 → 853 ms | 1,520 → 26 | 2,113 → 535 ms |
| 再照合 | 2,496 → 918 ms | 1,529 → 35 | 2,140 → 554 ms |
| Amazon在庫の取り直し | 1,480 → 937 ms | 1,139 → 586 | 1,346 → 777 ms |
| 取込（3ファイル、調査を新規作成・Amazon在庫なし） | 1,728 → 779 ms | 960 → 29 | 1,420 → 478 ms |

PERF-05の計測（変更前）からは、取込（3ファイル、Amazon在庫あり）で 4,738 → 1,025 ms、SQL 2,561 → 37、トランザクション 4,197 → 686 ms。調査の品番・SKUへの書き込みで10回以上のものはなくなった。Amazon在庫の経路に残る約590文は、スナップショットの1行ずつの保存（`insert amazon_inventory_snapshots 559`）で、PERF-13の対象。

- まとめて更新する UPDATE は1文100行にした。CASE の分岐は行ごとに先頭から比べられるので、1文の行数を増やすとSQLの実行時間が増える（300行ではSQLの時間が約2倍、所要時間はほぼ同じ）。

### PERF-08 取込CSVを順次読み込む

出典: C追加3。

- `追加の処理負荷調査.md` の3の修正案のとおり。種類の判定は先頭行だけ読み、取込本体はファイルから順に処理する。文字コード変換、重複チェック、行番号付きのエラーを維持する。
- 完了条件: 20 MiB程度のファイルで、変更前後のピークメモリを記録する。

**実装状況（2026-10-21）:** 実装済み。

- `InventoryImportService::rows()` はファイルから1行ずつ読むジェネレーターにした。文字コードの判定（ファイル全体が UTF-8 として正しいか）と Shift_JIS（CP932）からの変換は、約1 MiBずつ改行の直後で区切った塊ごとに行い、変換結果は一時ストリーム（2 MiBを超えると一時ファイル）に書く。改行のバイトは UTF-8 の多バイト文字にも Shift_JIS の2バイト目にも現れないので、区切って変換しても結果は変わらない。
- 種類の判定（`classifyFiles()`）はヘッダー行だけを読む。文字コードは取込本体と同じくファイル全体で判定する。
- 行番号はこれまでどおりCSVの行（レコード）で数え、重複チェックとエラーの文言も同じ。`InventoryCsvReadingTest`（2 MiBを超える Shift_JIS、セル内の改行、2バイト目が `0x5C` の文字、BOM付き UTF-8、行番号付きのエラー、重複）は変更前のコードでも同じ結果になることを確かめた。
- 計測用テストに「取込（3ファイル、各約20 MiB）」の経路を足した（対象外の行で水増しした Shift_JIS の3ファイル。変更前のコードでも止まらないよう、計測中は `memory_limit` を1Gにする）。

| 計測（3回の中央値） | 所要時間（前→後） | ピークメモリ（前→後） | トランザクション（前→後） |
| --- | --- | --- | --- |
| 取込（3ファイル、各約20 MiB） | 8,419 → 7,135 ms | +492.7 → +8.4 MB | 7,903 → 6,793 ms |

- 変更前は、ファイルの文字列・変換後の文字列・全行の配列を同時に持つため、3ファイルで約490 MB（1ファイルあたり平均160 MB程度）を使っていた。開発環境のPHPの既定の `memory_limit`（128M）では、上限に近いファイルの取込は失敗する。本番の設定値は未確認。
- 通常の大きさのファイルの経路は、SQL・ピークメモリとも変わらず、所要時間の差は計測の揺れの範囲だった。

### PERF-09 一括ダウンロードのZIPをファイルから直接作る

出典: Cl-7。

- `SurveyFileController::downloadZip()` で、`addFromString()` の代わりに `addFile()` を使い、ファイルの中身をメモリに読み込まない。
- 完了条件: ZIPの内容（ファイル名と中身）が変わらない。

**実装状況（2026-10-21）:** 実装済み。`addFile()` でディスクのファイルを直接ZIPに入れる（libzip が `close()` のときに読む）。`close()` に失敗したときは作りかけのZIPを消して例外にする。

- `SurveyFileDownloadTest` に、ZIPの各ファイルの名前と中身（Shift_JIS、BOM付き UTF-8、バイナリ）が保存したファイルと一致し、期限切れのファイルが入らないことを確かめるテストを足した。変更前のコードでも通ることを確かめた。同じファイルの既存テストが、ファクトリーの種類の乱数が重なってときどき失敗していたので、種類を明示した。
- 計測（約20 MiBの3ファイル、一時的なテストで測定）: ピークメモリ +81〜86 MB → +3.2 MB。ZIPの大きさは同じ。
- 所要時間は、この開発環境では 5.4〜7.9 秒 → 7.3〜11.0 秒と遅くなった。作業フォルダー（`/workspace`）が Windows のドライブを 9p でつないだものなので、libzip の細かい読み込みが遅くなるため。Linux のファイルシステム上では `addFromString()` と `addFile()` は同じ時間（26 MBで約2.1秒）だった。
- 時間のほとんどは圧縮にかかっている。libzip の既定の圧縮レベル（9）を zlib の既定の 6 にすると、26 MBのCSVで約2.1秒 → 約0.55秒、大きさは約10%増えた（Linux のファイルシステム上での単体の計測）。
- 依頼を受けて、圧縮レベルを 6 にした。同じ一時的なテストで、この開発環境では 7.3〜11.0 秒 → 約4.9 秒（3回とも 4.9〜5.0 秒）、ZIPは 8.9 MB → 9.8 MB。ここで残る時間の多くは 9p の読み込み。

### PERF-10 Amazonレポートを2本同時に待つ

出典: Cl-7。

- 自社在庫とFBA在庫のレポートの作成を両方先に依頼し、完成を並行して待つ。アクセストークンは1回だけ取得する。
- 一方が失敗したとき、FBAのレポートが作れないときの代替取得（`fetchFbaInventorySummaries`）、タイムアウトの扱いを現行どおりにする。

**実装状況（2026-10-21）:** 実装済み。`AmazonReportClient::fetchInventories()` で、アクセストークンを1回取得し、2本のレポートの作成を続けて依頼してから、まだできていないレポートだけを15秒ごとに確かめる。できたら自社在庫、FBA在庫の順に文書を取得する。`AmazonInventoryImportService::process()` はこれを呼ぶ。

- 失敗の扱いは変えていない。自社在庫のレポートが FATAL・CANCELLED になったら、FBAを待たずにその場で失敗にする。FBAのレポートが FATAL のときは、これまでどおり FBA在庫一覧API で取得する。
- 待つ回数の上限（`SP_API_POLL_ATTEMPTS`、既定40回）は、これまでどおりレポートごとに数える。2本を同時に待つので、最も長く待つ時間は約10分×2から約10分になる（取込の失効は2時間）。
- 1本だけ取得する `fetchOwnInventory()`・`fetchFbaInventory()` は、同じ処理で1本だけ扱うものとして残した（既存の単体テストが使う）。
- `AmazonReportClientTest` に、要求の順序（認証1回 → 作成2本 → 状態確認 → 文書取得）、FBAが FATAL のときの代替取得、自社在庫が FATAL のときに文書を取得せず失敗すること、片方が完成しないときのタイムアウトを確かめるテストを足した。
- 計測: 実際のSP-APIを呼ぶと設定先DBに書き込むため、変更後は測っていない。手元のDBに残る変更前の成功10件では、開始から自社在庫の取得まで 34〜48 秒、そこからFBA在庫の取得まで 33〜80 秒、全体で 69〜119 秒だった。FBAの待ちが自社在庫の待ちと重なるので、全体はおおむね遅い方のレポートの時間（35〜80 秒程度）になる見込み。

### PERF-11 在庫推移の出力を順次処理にする

出典: C追加5。

- `追加の処理負荷調査.md` の5の修正案のとおり。CSVは日付単位などで順に書き出す。外部APIは応答仕様を変えないため、まず実運用の最大期間と応答時間を測り、上限やページングの要否を判断する。

**実装状況（2026-10-21）:** 実装済み。

- `InventoryTrendCsvExporter::rows()` を、1日分ずつ読み込んで行を返すジェネレーターにした。最初に期間内の調査のIDと日付、日ごとに使うAmazon取込のIDだけを読む。そのあと日付順に、その日の調査品番・調査SKUと、調査にない品番のスナップショットだけを読む。以前は期間内の全スナップショットを読んでいたが、調査にある品番の分は使わないので読まない。どの調査・取込を使うか、行の順序は変えていない。
- CSV出力は、この行を1行ずつ一時ファイルに書く（これまでどおり）。
- 外部日次APIは、全行を配列にせず、1行ずつJSONにして書き出す（`response()->stream()`）。本文は以前の `response()->json()` と同じバイト列になる（エスケープも同じ）。`Content-Length` は付かなくなる。最初の日の分を読み込んでから応答を始めるので、最初の読み込みで失敗したときはこれまでどおりエラー応答になる。2日目以降の読み込みで失敗すると、200のまま途中で切れたJSONになる（DBの障害のときだけ）。
- `ExternalInventoryApiTest` に、複数日・同日の複数調査・Amazon在庫だけの品番・日本語や「/」「"」を含む値で、本文が `json_encode()` で全体を作ったときと同じバイト列になることを確かめるテストを足した（0件のときも）。変更前のコードでも通ることを確かめた。
- 計測は `InventoryTrendExportBenchmarkTest` で行う（`RUN_BENCHMARKS=1 php artisan test tests/Feature/InventoryTrendExportBenchmarkTest.php`）。112品番・817 SKUの調査を毎日1件（日曜は調査なしでAmazon取込だけ）、テスト用のDBに入れて、全品番で期間ごとに測った。開発環境は Xdebug が有効で PHP が数倍遅くなるため、`XDEBUG_MODE=off` で測った。
