# 性能改善

システムの処理負荷と無駄を減らすための調査結果とチケット。チケット番号は `PERF-xx` で管理する。

## 調査結果

- [調査履歴の全件明細読込を解消.md](./調査履歴の全件明細読込を解消.md)（Codex）: ログイン時に全調査の全SKU明細を取得している問題と修正方針。
- [追加の処理負荷調査.md](./追加の処理負荷調査.md)（Codex）: CrossWalker同期、同日再取込、CSV読込、コミット後の再照合、在庫推移の出力など。
- [Claudeによる追加調査.md](./Claudeによる追加調査.md)（Claude）: アイコンフォント、応答の未使用項目、Amazon在庫の1行ずつの更新、和文フォント、結果画面の再描画など。Codexの修正案への補足も含む。

以下、チケットの「出典」は、C＝Codex（調査履歴＝`調査履歴の全件明細読込を解消.md`、追加＝`追加の処理負荷調査.md` の番号）、Cl＝Claude（`Claudeによる追加調査.md` の番号）。

## 進め方

1. **すぐ効くもの（PERF-01〜02）:** 変更が小さく、初回表示と通信量に効く。
2. **調査履歴と結果画面（PERF-03〜04）:** ログイン時の全明細取得をやめる。画面とAPIの両方を変える。
3. **取込経路（PERF-05〜08）:** 先に計測（PERF-05）してから、同期と書込みを差分にする。
4. **個別の改善（PERF-09〜11）:** 単独で進められる。
5. **判断が必要なもの（PERF-12〜13）:** 見た目や運用の方針を決めてから進める。

## チケット一覧

### PERF-01 アイコンフォントを使うアイコンだけにする

出典: Cl-1。

- Material Symbolsの読込を、使う軸（`opsz` 24、`wght` 400、`FILL` 0～1、`GRAD` 0）と、使うアイコンだけ（`icon_names=`）に絞る。現行3,907 KB → 約9 KB。
- 使うアイコン名の一覧をコードで1か所に持ち、テンプレートやデータで使うアイコンが一覧に入っていることをテストで確かめる。`icon_names` はアルファベット順に並べる必要がある。
- `display=block` を見直すか検討する（アイコン名の文字が一瞬見えるのを避けるため、ブロックのままでもよい）。
- 完了条件: すべての画面でアイコンが表示される（塗りつぶしのアイコンを含む）。読み込むフォントの大きさを変更前後で記録する。

**実装状況（2026-10-20）:** 実装済み。アイコン名の一覧は `resources/js/constants/icons.ts`（57種類）。`AppIcon` などアイコン名を受け取るプロパティとデータを `IconName` 型にしたので、一覧にない名前は `npm run check` の型チェックで失敗する。一覧が並んでいること、使われていない名前がないことは `icons.test.ts` で確かめる。フォントは `app.ts` から読み込み、`app.blade.php` には接続の先読みだけを残した。

| 計測（ブラウザーで初回表示時に取得したアイコン用フォント） | 大きさ |
| --- | --- |
| 変更前（全軸・全アイコン） | 3,907 KB |
| 変更後（使う軸・使うアイコンだけ） | 9 KB（CSS 1 KB） |

### PERF-02 調査の応答から使わない項目と読込を外す

出典: Cl-2、Cl-4。

- `SurveyResource` のSKUから `colorName`・`tqCode`・`tqColorNo`・`tqSize`・`stock.amazonTotal`・`stock.mallTotal`・`stock.grandTotal` を外す。TypeScriptの型とテスト用のダミーデータも合わせる。
- `InventoryImportService::import()` の最後の読込から `amazonImport.snapshots` を外す。
- 公開外部API（`/api/v1/inventory/daily`）の応答は変えない。
- 完了条件: 一覧と明細の応答の大きさを変更前後で記録する（計測時点で一覧1,765 KB → 1,128 KB、明細248 KB → 160 KBの見込み）。画面の表示とExcel出力が変わらない。

**実装状況（2026-10-20）:** 実装済み。調査の応答のSKUは `id`・`skuCode`・`size`・`asin`・`stock`（倉庫ごとの6値）・`memo` だけにした。合計は画面側の `utils/stock.ts` で計算しており、その規則（未確定は `null`、ASINのないSKU、旧方式、Amazonなし）はVitestで確かめている。PHPのテストは、合計の代わりに元の値と、外した項目が返らないことを確かめる。品番グループとCrossWalker検索の応答（`ProductResource`）は別の応答なので変えていない。

| 計測（設定先DBの全23調査、読み取りのみ） | 変更前 | 変更後 |
| --- | --- | --- |
| 一覧（`GET /api/surveys` と同じ内容） | 1,765 KB（実際の応答形式で約1,828 KB） | 1,128 KB（実際の応答形式で1,166 KB） |
| 直近の調査1件（`GET /api/surveys/{id}`） | 248 KB（約259 KB） | 160 KB（167 KB） |

「実際の応答形式」は日本語をエスケープしたJSON（Laravelの既定）。変更前の値は、外した項目を計測の中で再現した概算。取込の応答では、Amazonスナップショット（直近の取込で559行）を読み込まなくなった。

### PERF-03 調査履歴の一覧を概要だけにする

出典: C調査履歴（文書全体）。

- `調査履歴の全件明細読込を解消.md` の修正方針と完了条件のとおり。`GET /api/surveys` を概要だけにし、明細は `GET /api/surveys/{id}` で必要なときに取得する。
- 一覧の集計値（全倉庫ゼロ・一部ゼロ、Amazonの状態、ファイルの状態など）は、現行の `summarizeSurvey()` と一致させる。
- 在庫調査履歴、在庫調査結果、ファイル管理、連携ステータス、上部バーの表示を確認する。

**実装状況（2026-10-20）:** 実装済み。

- 一覧（`GET /api/surveys`）は `SurveySummaryResource` で概要だけを返す。品番数・SKU数・全倉庫ゼロ・一部ゼロ・Amazonの状態は、`SurveySummaryService` が `survey_skus` の集計クエリ1本で求める（SKUの行は読み込まない）。Amazonの状態の規則は `Survey::resolveAmazonInventoryStatus()` などに切り出し、明細の `SurveyResource` と共通にした。
- 画面のストアは「一覧の概要（`summaries`）」と「取得した明細（`details`）」に分けた。結果画面は開いたときに明細を取得し（URLを直接開いた場合も）、取得中・見つからない・読み込めない（再試行できる）を表示する。前回比は直前の調査の概要で比べる。取込・再照合・再読込で明細を取得したときは、その調査の概要も明細から作り直す（`toSurveySummary`）。
- 一致の確認: 変更前の明細の応答（全23調査、5,911 SKU）を保存しておき、画面の `summarizeSurvey()` で数えた値と、新しい一覧の集計値（設定先のMySQLで実行）を比べ、品番数・SKU数・全倉庫ゼロ（計299）・一部ゼロ（計5,079）・Amazonの状態・ファイルがすべて一致した。

| 計測（設定先DBの全23調査、読み取りのみ） | 変更前 | 変更後 |
| --- | --- | --- |
| 一覧の処理時間（関連データの読込とJSON生成） | 2,523 ms | 192 ms |
| 一覧の応答 | 1,166.5 KB（PERF-02の後） | 23.9 KB |
| PHPのピークメモリ（フレームワーク分を含む） | 39.3 MB | 15.7 MB |

未確認: 本番と同じ配信条件でのブラウザーの表示時間（ローカルはViteの開発サーバーのため）と、履歴がさらに増えた条件での計測。集計クエリは `survey_skus` の行数に比例するが、SKUの行をPHPに読み込まない。

### PERF-04 在庫調査結果の再取得と再描画を減らす

出典: C追加（優先度が低い候補の1つ目）、Cl-6。

- 30秒ごとの再取得を、Amazon在庫が取込待ち・一部未取得のときと、画面が見えているときに限る。Amazon取込完了後の自動反映は維持する。
- 品番カードの `v-memo` が効くように、内容が変わっていない品番は同じオブジェクトを使い回す。行の状態（全倉庫ゼロ、総数など）は1行につき一度だけ計算する。
- PERF-03の後に行う（明細の取得方法が変わるため）。

**実装状況（2026-10-20）:** 実装済み。

- 30秒ごとの再取得は、SP-API調査のAmazon在庫が取込待ち・一部未取得で、画面が見えているときだけ行う。別のタブに移ると止め、戻ったときに待っている状態ならすぐ1回取り直す。反映済みの調査は取り直さない（手動の「最新の在庫を再読込」はこれまでどおり）。
- 在庫表は、行ごとの状態・合計・構成を一度だけ計算した表示用のデータ（`ProductView`・`SkuRowView`）から描く。品番ごとに画面に出る値の文字列（snapshot）を持ち、前回と同じなら同じオブジェクトを使うので、品番カードの `v-memo` が効く。再取得で中身が同じなら描き直さず、変わった品番のカードだけ描き直す（`SurveyResultPage.test.ts` でカードの描画回数を確かめている）。

| 計測（実データの直近の調査817 SKU、同じ内容を返す再読込を5回、ブラウザーのメインスレッドの処理時間） | 3回の計測 |
| --- | --- |
| 変更前 | 865 ms、812 ms、673 ms |
| 変更後 | 284 ms、189 ms、176 ms |

ローカルのViteの開発サーバーで、APIの応答はブラウザー側で返して計測した（PERF-03適用後の状態との比較）。本番のビルドではどちらも短くなるが、比率の目安になる。

### PERF-05 取込経路を計測する

- ファイル取込、同日の追加取込、再照合、Amazon在庫取込、品番グループ保存について、所要時間、SQLの発行数（種類別）、トランザクションの長さ、PHPのピークメモリを測る。

- 結果をこのフォルダーに記録し、PERF-06〜08の前後比較に使う。

**実装状況（2026-10-20）:** 実施済み。結果は [PERF-05_取込経路の計測.md](./PERF-05_取込経路の計測.md)。計測用のテスト `ImportPathBenchmarkTest` を追加した（`RUN_BENCHMARKS=1` のときだけ動く）。どの取込経路でもSKUマスタ817件の削除・再登録、調査の929行の作り直し、Amazon在庫の559回のUPDATEが発生し、トランザクションが2.6〜4.2秒続いていた。時間の大半はSQLの実行ではなく1行ずつのモデル作成・更新にかかっている。

### PERF-07 調査の品番・SKUを差分更新し、Amazon在庫を作成時に入れる

出典: C追加2、C追加4、Cl-3。

- `writeProducts()` を、品番コード・SKUコードをキーにした差分更新にする（`追加の処理負荷調査.md` の2の修正案）。
- 調査SKUを作るとき、その日の最新の成功取込のAmazon在庫を最初から入れる。`syncSurvey()` は差分がなければ書き込まず、書き込むときもまとめて更新する。Amazon取込の成功時の反映（`syncDate()`）も同様にする。
- コミット後の再照合は、適用済みの取込から変わっていなければ省く（`追加の処理負荷調査.md` の4の修正案）。並行して取込が完了する競合のテストを先に作る。
- メモ、グループ所属、未確定（`null`）と確定値、ASINのないSKU、古いSKUの削除、並び順、IDの扱いを現行どおりにする。
