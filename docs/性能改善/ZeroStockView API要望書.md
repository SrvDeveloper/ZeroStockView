# ZeroStockView 外部API 要望書

| 項目 | 内容 |
| --- | --- |
| 作成日 | 2026年10月21日 |
| 依頼元 | Mall Insight（ECモール統合分析システム）開発チーム |
| 対象 | ZeroStockView 外部API `v1`（「ZeroStockView：API仕様書」） |

## 1. 背景

Mall Insight は、ZeroStockView から日次のSKU別在庫を取得し、在庫の推移、欠品の判定、需要予測（欠品していた日を除いた平均日販）に使っています。商品（品番・SKU・子ASIN）は CrossWalker から取得しており、ZeroStockView の在庫は CrossWalker のSKUコードにひも付けています。

現在利用しているのは次の1つだけです。

```
GET /api/v1/inventory/daily?from={YYYY-MM-DD}&to={YYYY-MM-DD}
```

- 毎朝10時と画面の操作で取得しています。ZeroStockView 側の在庫取込が毎朝手動のため、ゆとりを持たせて10時にしています。
- 再照合による値の変化を拾うため、毎回、直近7日分を取り直しています。
- `product_code` は指定せず、全品番を31日ずつ区切って取得しています。

10月19日の改修（在庫数が null になる、調査の無い日も Amazon だけの行が返る）は、事前に連絡をいただいたおかげで、null を0と読み違えずに対応できました。ありがとうございました。

本書の件数は、Mall Insight の開発用DBに2026年10月21日時点で保存した値です（在庫の履歴は2026年9月16日から）。

## 3. 要望の詳細

### 要望1 API仕様書の更新（優先度：高）

Mall Insight が受け取っている仕様書は、10月19日の改修より前の内容です。次の点を仕様書に反映し、改訂版をいただけますか。

| 項目 | 今の仕様書 | 実際の動き |
| --- | --- | --- |
| 在庫数の6項目（`amazonOwn` など） | `integer` | `integer \| null`。null はその区分をまだ取り込んでいないか、そのSKUが取込の対象外であることを表す |
| 調査の無い日（土日など） | データを返さない | Amazon の取込が済んでいれば、Amazon だけの行が返る（BOSS・フリー在庫・ECストックは null） |
| `brand`・`category`・`size` | `string` | 商品マスタの無いSKUでは `null` |
| 1回に指定できる期間 | 365日以内 | 31日以内（超えると `422`「対象期間は31日以内で指定してください。」） |

期間の上限は31日のままで問題ありません。365日に広げていただく必要はなく、仕様書の記載を実際に合わせていただければ十分です。

### 要望3 日ごとの取込状況の取得（優先度：高）

#### 目的

今の Mall Insight は、ある日にどの区分の在庫がそろったかを、行の中の null から推し量っています。また、行が1件も返らない日について、調査をしない日なのか、まだ取り込んでいないだけなのかを区別できません。たとえば、10月2日（金）と10月10日（金）は1行も返っていません。

日ごとの取込の状況を取得できれば、次のことができるようになります。

- 在庫の鮮度を正しく判定できる（調査をしない日を「遅れ」と警告しない）。
- 取込が済んだ時刻に合わせて取得でき、毎朝10時の決め打ちをやめられる。

#### インターフェースの案

あくまで案です。パス・項目名・形式は ZeroStockView 側で決めてください。

**取得：** `GET /api/v1/inventory/imports?from={YYYY-MM-DD}&to={YYYY-MM-DD}`

```json
{
  "data": [
    {
      "date": "2026-10-17",
      "surveyed": false,
      "sources": {
        "amazon": { "status": "imported", "importedAt": "2026-10-17T09:12:00+09:00" },
        "boss": { "status": "not_scheduled", "importedAt": null },
        "freeStock": { "status": "not_scheduled", "importedAt": null },
        "ecStock": { "status": "not_scheduled", "importedAt": null }
      }
    },
    {
      "date": "2026-10-21",
      "surveyed": true,
      "sources": {
        "amazon": { "status": "imported", "importedAt": "2026-10-21T09:05:00+09:00" },
        "boss": { "status": "imported", "importedAt": "2026-10-21T09:20:00+09:00" },
        "freeStock": { "status": "imported", "importedAt": "2026-10-21T09:20:00+09:00" },
        "ecStock": { "status": "pending", "importedAt": null }
      }
    }
  ],
  "meta": { "from": "2026-10-17", "to": "2026-10-21", "count": 2 }
}
```

| 項目 | 型 | 説明 |
| --- | --- | --- |
| `date` | string | 在庫調査日 |
| `surveyed` | boolean | その日に在庫調査を行うか（行った・行う予定なら `true`、休業日などで行わないなら `false`） |
| `sources.{取込元}.status` | `imported` \| `pending` \| `not_scheduled` | 取込済み・まだ取り込んでいない・その日は取り込まない |
| `sources.{取込元}.importedAt` | string \| null | 取り込んだ日時（日本時間、ISO 8601） |

取込元の分け方（`amazon` は `amazonOwn`・`amazonFba`、`boss` は `bossOwn`・`bossRfc` など）は、ZeroStockView の実際の取込の単位に合わせてください。

### 要望4 Amazon の在庫数が null になる理由の区別（優先度：中）

Amazon の在庫数（`amazonOwn`・`amazonFba`）が null になる理由は、次の2つがあると理解しています。

1. その日の Amazon の在庫をまだ取り込んでいない。
2. そのSKUが Amazon の取込の対象外である（子ASINが無いなど）。

Mall Insight では、2つ目は「Amazon では売っていないので0」、1つ目は「まだ分からない」として扱いを分けています。今は CrossWalker の子ASINの有無で区別していますが、CrossWalker に無いSKUでは区別できません。

行の中で理由を区別できるようにしていただけませんか。たとえば次のような項目です（案）。

```json
{
  "sku": "spc-006-3",
  "amazonOwn": null,
  "amazonFba": null,
  "amazonStatus": "not_applicable"
}
```

`amazonStatus` は `imported`（取込済み）・`pending`（まだ取り込んでいない）・`not_applicable`（取込の対象外）を想定しています。要望3で日ごとの取込状況が分かれば、`pending` と `not_applicable` だけを区別できれば足ります。

### 要望5 商品マスタの CrossWalker との一致（優先度：中）

ZeroStockView の商品と CrossWalker の商品に、次のずれがあります。

| ずれ | 内容 |
| --- | --- |
| CrossWalker に無いSKU | `eb23-50-cry`、`eb23-50-yel`、`eb23-50-blu`、`eb23-50-cor`、`eb23-50-ppl`、`eb23-50-ras`、`siwa-case01-1`、`siwa-case01-2`、`siwa-case01-3` の9件 |
| カテゴリー名の違い | `fl-3000`・`flh-001ph` が、ZeroStockView では「調光老眼鏡」、CrossWalker では「老眼鏡」 |

1. 9件のSKUについて、CrossWalker への登録漏れなのか、ZeroStockView だけで使っているコードなのかを教えてください。登録漏れであれば、CrossWalker に登録するよう依頼します。
2. カテゴリーについては、Mall Insight では ZeroStockView のブランド・カテゴリーを使っておらず、影響はありません。ただし、ZeroStockView の商品マスタを CrossWalker のAPIから取るようにしていただければ、このようなずれ自体が起きなくなります。ご検討いただければ幸いです。

### 要望6 変わった行だけの取得（優先度：低）

返却後の取込や再照合で値が変わる分は、今は直近7日分を毎回取り直して拾っています。今の量（1日641 SKU、7日分で約4,500行）なら問題はありません。今後、量が増えたときのために、次のどちらかがあると助かります。

- 行ごとの更新日時（例：`updatedAt`）
- 指定日時より後に変わった行だけを返す条件（例：`updated_since`）

### 要望7 入力エラーの文言の翻訳（優先度：低）

存在しない品番を `product_code` に指定すると、`errors` の文言が `validation.exists` のような翻訳キーのまま返ります。Mall Insight は `product_code` を使っていないため影響はありません。

## 4. 今のままで問題ないこと

次の点は確認済みで、変更の必要はありません。

- 在庫がすべて0のSKUも省かれずに返ること（10月21日は77 SKU）。0在庫と、行が無いことを区別できています。
- 回数制限（毎分60回）。1回の取得で呼ぶのは数回です。
- `product_code` の指定と、行の `brand`・`category`。Mall Insight では使っていないため、変更・廃止しても影響はありません。

## 5. 運用面のお願い

1. **形式が変わるときは、今後も事前に連絡してください。** Mall Insight は、行の `date`・`sku`・在庫数の6項目と `data` の形を使っています。
2. **本番サーバーの接続元IPを許可リストに追加してください。** 本番環境のIPアドレスは別途連絡します。
