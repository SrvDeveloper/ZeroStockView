# Claudeによる追加調査

調査日: 2026-10-20。コードを確認し、設定先DBを読み取り専用で計測した。処理の変更や取込の実行はしていない。Codexの調査（[調査履歴の全件明細読込を解消.md](./調査履歴の全件明細読込を解消.md)、[追加の処理負荷調査.md](./追加の処理負荷調査.md)）は内容を確認し、妥当と判断した。ここにはCodexの調査にない点と、Codexの修正案への補足を記す。

調査時点のデータ: 調査23件、調査SKU 5,911行、品番112件、SKUマスタ826行、直近の調査は817 SKU、直近の成功したAmazon取込は559 SKU、Amazonスナップショット計2,930行。

## Codexの修正案への補足

- **CrossWalker同期の差分更新:** SKUマスタには `child_asin` の一意制約と、`tq_item_no`・`tq_color_no`・`tq_size` の組の一意制約がある。CrossWalker側で2つのSKUの値が入れ替わると、1行ずつ更新する途中で一意制約に違反する。現行の「全件削除して再登録」はこれを避けている。差分更新にするときは、入れ替わりのケースを先にテストにする。
- **コミット後のAmazon再照合:** 下の3（Amazon在庫の1行ずつの更新）と同じ `syncSurvey()` の問題なので、一緒に直すと効率がよい。

## 新たに見つかった点

### 1. アイコン用フォントが3.9 MBある

`src/resources/views/app.blade.php` は、Google FontsのMaterial Symbols Outlinedを全軸（`opsz` 20～48、`wght` 100～700、`FILL` 0～1、`GRAD` -50～200）で読み込んでいる。`AppIcon.vue` が使うのは `FILL` 0/1、`wght` 400、`GRAD` 0、`opsz` 24だけ。`display=block` のため、初回表示ではフォントが届くまでアイコンが表示されない。

Google Fontsから実際に取得したフォントファイルの大きさ:

| 指定 | 大きさ |
| --- | --- |
| 現行（全軸） | 3,907 KB |
| 使う軸だけ（`opsz,wght,FILL,GRAD@24,400,0..1,0`） | 451 KB |
| 使う軸＋使うアイコン約60種類だけ（`icon_names=`） | 約9 KB |

アイコン名はテンプレートの文字列のほか、データ（マニュアルの節、入口ページのカードなど）からも渡している。使うアイコンを絞る場合は、一覧をコードで管理し、漏れをテストで防ぐ。

### 2. 調査の応答の約36%が画面で使わない項目

`SurveyResource.php` はSKUごとに次の7項目を返すが、画面のコードはどれも読んでいない（テスト用のダミーデータを除く）。

- `colorName`（常に空文字）
- `tqCode`・`tqColorNo`・`tqSize`（`tqSize` は `size` と同じ値）
- `stock.amazonTotal`・`stock.mallTotal`・`stock.grandTotal`（画面側の `utils/stock.ts` で計算し直している）

全調査の応答（一覧APIと同じ関連データ）で計測すると、1,765 KB → 1,128 KB、直近の調査1件で248 KB → 160 KBになる（`JSON_UNESCAPED_UNICODE` で計測。実際の応答は日本語がエスケープされるため、もう少し大きい）。一覧APIの作り直し（Codexの最優先項目）とは独立に、一覧と明細の両方にすぐ効く。

### 3. 取込のトランザクション内でAmazon在庫を1行ずつ更新する

`InventoryImportService::import()` は、`writeProducts()` で調査SKUをAmazon在庫 `null` の状態で1行ずつ作成した直後に、`SurveyAmazonInventorySyncService::syncSurvey()` で同じSKUへAmazon在庫を1行ずつ `save()` する。現在のデータでは、品番112件・SKU 817件の作成に続いて、約559回のUPDATEが同じトランザクションで発生し、その間は調査の行をロックしている。Amazon取込の成功時（`syncDate()`）の反映も同じく1行ずつ。発行回数はコードと件数からの推定で、所要時間は未計測。

**修正案:** 作成時にその日の最新の成功取込のAmazon在庫を入れておき、同期は差分がなければ書き込まない。反映が必要なときもまとめて更新する。`null`（未取得）と確定値、ASINのないSKU（対象外）、並行して取込が完了する競合の扱いは現行どおりにする。

### 4. 取込の応答のために使わないAmazonスナップショットを読み込む

`InventoryImportService::import()` は最後に `load(['products.skus', 'files', 'amazonImport.snapshots'])` を呼ぶが、`SurveyResource` はスナップショットを使わない。現在は1回の取込で559行を余分に読み込む。`amazonImport` だけにすればよい。

### 5. 和文フォントのCSSが539 KBあり、描画を止めている

`vite.config.js` でNoto Sans JPを5つの太さ（400・500・600・700・800）で自前配信しており、生成されるCSSは `@font-face` が605個、539 KB（gzip 166 KB）。`@fonts` で `<head>` に読み込むため、このCSSを読み終えるまで描画が始まらない。5つの太さはすべて画面で使っている（Tailwindの `font-medium`・`font-semibold`・`font-bold`・`font-extrabold`）。

**修正案:** 可変フォント（太さを1つのファイルで持つ）にできるか確認する。できない場合は、使う太さを減らす。見た目に影響するので、変更前後の画面を比べて判断する。

### 6. 在庫調査結果画面が30秒ごとの再取得で全行を描き直す

Codexは30秒ごとの再取得の通信量を挙げているが、描画の負担もある。`SurveyResultPage.vue` は品番カードに `v-memo="[product, canEditMemo]"` を付けているが、`filteredProducts` が再計算のたびに新しいオブジェクト（`{ ...p, skus: ... }`）を作るため、効いていない。再取得のたびと、メモを1件保存するたびに、表示中の全行（直近の調査で817行）を描き直す。各行のテンプレートは `skuRowState()` などを1行あたり数回呼び、そのたびに在庫総数を計算し直す。

**修正案:** 内容が変わっていない品番は同じオブジェクトを使い回すか、`v-memo` の依存を品番の更新を表す値にする。行の状態はまとめて一度だけ計算する。30秒ごとの再取得の条件の見直し（Codexの案）と一緒に行う。

### 7. その他（影響は小さい）

- **Amazonレポートを1本ずつ待つ:** `AmazonReportClient` は自社在庫とFBA在庫のレポートを、作成依頼 → 完成待ち（15秒間隔で最大40回）→ 取得の順に1本ずつ処理する。2本とも先に作成を依頼してから待てば、完了までの時間をほぼ半分にできる。サーバーの負荷ではなく所要時間の問題。アクセストークンも2回取得している。
- **一括ダウンロードでファイルを丸ごとメモリに読む:** `SurveyFileController::downloadZip()` は各ファイルを `Storage::get()` で読み、`ZipArchive::addFromString()` に渡す。文字列は `close()` まで保持されるため、最大3ファイル×20 MiBを同時にメモリに持つ（PHPの `memory_limit` は128M）。`addFile()` でディスクから直接追加すればよい。
- **Amazonスナップショットの保存期限がない:** 1回の取込で約560行ずつ増え、削除の仕組みがない。スナップショットは `createMany()` で1行ずつINSERTしている。在庫推移が過去のAmazon在庫を参照するため、残す期間は運用で決める。
- **取込の開始時に対象品番とSKUを2回読み込む:** `import()` は全SKUを含めて対象品番を読み込み、CrossWalker同期の後に `loadTargets()` で読み直す。
