# BHR-02 再現の計算と照合

**目的:** 読み込んだ在庫変動履歴（BHR-01）と、期間内に BOSS のレポートを取り込んだ調査（基準の調査）から、補完する日の 9:00 時点の BOSS 在庫を SKU・倉庫ごとに計算する。基準の調査と履歴が合わない SKU を見つける。

**依存:** BHR-01

## 作業

- `app/Services/BossInventoryReconstructor.php`（新規）を作る。データベースに書き込まない（計算だけ）。入力と出力は次のとおり。
  - 入力: BHR-01 の読込結果、対象の SKU（`Product::surveyTargets()` の有効な SKU）、基準の調査（期間内の調査で、BOSS のレポートを取り込んだもの）の SKU・倉庫ごとの BOSS 在庫、補完する日の一覧
  - 出力: 補完する日 × SKU コード → `boss_own_stock`・`boss_rfc_stock`（`NULL` を含む）と、照合の結果
- 再現の規則は README の「再現の考え方」のとおり。再現する時刻は定数 `BASIS_TIME = '09:00:00'`（README の前提 1）。
- 基準の調査の値は `survey_skus.boss_own_stock`・`boss_rfc_stock`（実在庫 − 引当済）を使う。基準の調査が複数あるときは、補完する日に近い方を使う（どれを使っても、期間内に行のない SKU なら同じ値になる。違えば照合の不一致として扱う）。
- **照合（README の前提 4）**: 基準の調査の日ごとに、SKU・倉庫が、その日の「いずれかの時刻」で履歴の値と一致するかを調べる。
  - 候補の時刻は、その日の 0:00 と、その日の履歴の各行の直後。基準の調査の SKU・倉庫が、どの候補の時刻でも一致しなければ不一致とする。
  - 全体で最も多くの SKU が一致する時刻を「レポートを出力した時刻（推定）」として返す（確認画面に出す）。その時刻で一致しない SKU も不一致として扱う。
  - 不一致の SKU・倉庫は、補完する日すべてで `NULL` にする。
  - 推定したレポートの時刻が、履歴の最初の行より前になる基準の調査は使わない（レポートの出力から履歴の始まりまでの動きが抜けていて、期間内に行のない SKU では気づけないため）。使える基準の調査が残らなければ、補完できないとして結果に理由を入れる（BHR-04 で 422 にする）。
- 次の SKU・倉庫も `NULL` にして、理由付きで結果に入れる。
  - 補完する日の 9:00 をまたいで、つながりの切れ目（BHR-01）がある
  - 9:00 時点の値がマイナス
- 補完する日のうち、9:00 が履歴の期間の外（履歴の最初の行より前、または最後の行より後で、かつその間を基準の調査で埋められない）にある日は、補完できない日として結果に入れる。
- 結果には、補完する日ごとの「値が入る SKU 数」「`NULL` になる SKU 数とその理由ごとの件数」と、不一致の SKU・倉庫の一覧（最大 100件）を入れる。

## 完了条件

- PHPUnit で次を確認する（架空のデータ）。
  - 9:00 より前の最後の行の変動後の値、9:00 より後の最初の行の変動前の値、期間内に行のない SKU が基準の調査の値になること、基準の調査にもない SKU が `NULL` になること
  - 金曜のレポート・土日・月曜のレポートの組み合わせで、金曜から進めた値と月曜から戻した値が一致すること
  - 照合: レポートを出力した時刻の推定、基準の調査と合わない SKU が補完する日すべてで `NULL` になること
  - つながりの切れ目・マイナスの値・期間外の日の扱い
  - 実在庫・引当済が同じ数だけずれる行（出荷が履歴に出ない経路）があっても、実在庫 − 引当済が合えば一致として扱うこと
- Pint が通る。

**実装状況（2026-10-23）:** `BossInventoryReconstructor`（計算だけで、データベースには書き込まない）と、結果を持つ `BossInventoryReconstruction` を追加した。入力は、BHR-01 の読込結果、対象の SKU コード、基準の調査の日ごとの SKU・倉庫の BOSS 在庫（配列）、補完する日。データベースから入力を集めるのは BHR-04 で行う。チケットから決めた点は次のとおり。

- レポートを出力した時刻の推定で、一致する SKU・倉庫の数が同じ候補が複数あるときは、遅い方の時刻を選ぶ（履歴の始まりより前と判定しにくくするため。同じ数なら、どの時刻でも値は変わらない）。
- 期間内に行のない SKU・倉庫で、基準の調査どうしの値を比べるときは、レポートに載っていない（`NULL`）調査は比べない。補完する日には、近い基準の調査から順に、値のあるものを使う（最初は `NULL` も違う値として扱っていて、ある日のレポートに載っていない SKU が不一致になっていた）。
- 補完する日の 9:00 が、履歴の最初の行より前か最後の行より後なら、補完できない日にする（基準の調査のレポートは、履歴の最初の行以降に出力したものだけを使うので、履歴の外を基準の調査で埋めることはない）。
- 基準の調査の日が履歴の期間（最初の行の日〜最後の行の日）の外なら、その基準の調査は使わない。
- 結果の「値が入る SKU」は、自社倉庫と RFC倉庫の両方に値が入る SKU。どちらかが `NULL` なら「`NULL` になる SKU」に数え、理由ごとの件数は SKU 単位で数える。
- 手元のデータベースの実際の調査（10/16・10/19・10/20 を基準）と検証に使った履歴で計算し、推定したレポートの時刻が 10/16 07:37、10/19 09:13（検証の結果の範囲内）になり、不一致は0件、10/17・10/18 とも 272 SKU すべてに値が入ることを確かめた。
