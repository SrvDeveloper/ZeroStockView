# BOSS在庫の休日補完計画

BOSS の在庫レポート（倉庫毎の在庫数レポート）は手作業で出力するため、出勤しない休日は BOSS の在庫が歯抜けになる。BOSS から出力できる「在庫変動履歴」を使って、休日の BOSS 在庫を再現し、調査に保存できるようにする計画とチケット。

- チケット番号は `BHR-xx`（BOSS History Reconstruction）で管理する。
- 補完するのは BOSS（自社倉庫・RFC倉庫）だけ。Amazon は SP-API で毎日取れる。TQ（フリー在庫・ECストック）は、休日は歯抜けのまま残る。

## 検証結果（2026-10-23）

10/16〜10/20 の在庫変動履歴（701行）と、10/16・10/19・10/20 の在庫レポート（各 1,512 SKU、自社倉庫・RFC倉庫で 3,024行）で確かめた。

| 照合 | 実在庫 − 引当済（調査に保存する値） | 実在庫・引当済それぞれ |
| --- | --- | --- |
| 10/16 のレポート＋履歴 → 10/19 のレポート（土日をはさむ） | 3,024 / 3,024 一致 | 3,023 / 3,024 一致 |
| 10/19 のレポート＋履歴 → 10/20 のレポート | 3,024 / 3,024 一致 | 3,022 / 3,024 一致 |

- 履歴の各行は「変動前／変動後」の実在庫と引当済、それに「変動後実在庫 - 変動後引当済」を持つ。調査の BOSS 在庫（`実在庫 (倉庫毎) - 引当済 (倉庫毎)`）と同じ定義なので、行の値をそのまま使える。
- 同じ SKU・倉庫の行は、時刻順に並べると「変動前」が1つ前の行の「変動後」とつながる。同じ秒に複数の行があるときは、このつながりで順番が1つに決まる。
- 実在庫・引当済それぞれでは合わない3件（自社倉庫の `twig1-01m`、`twig2-02r`）は、実在庫と引当済が同じ数だけ減っているのに履歴に行がない。出荷が履歴に出ない経路があるとみられる。出荷では「実在庫 − 引当済」は変わらないので、調査の値には影響しない。
- レポートを出力した時刻は、履歴との一致の仕方から割り出せる（10/16 は 07:37〜09:12、10/19 は 08:59〜09:13、10/20 は 09:37〜09:44。10/20 はファイル名の 09:43:52 と合う）。
- 出てきた処理種別は、API注文引当、自社注文出荷実績、API注文出荷実績、在庫調整（増・減）、RSL在庫増減、出荷引当キャンセルの6種類。返品・倉庫間の移動などは、この期間には出てこなかった。

検証に使った実データ（注文番号やショップ名を含む）はリポジトリに入れない。テストは架空のデータで作る。

## 再現の考え方

在庫変動履歴は、期間内のすべての在庫の変化の記録として扱う。ある時刻 `t` の SKU・倉庫の「実在庫 − 引当済」は、次の順で決める。

1. 履歴に `t` 以前の行があれば、その最後の行の「変動後実在庫 - 変動後引当済」。
2. なければ、`t` より後の最初の行の「変動前実在庫 - 変動前引当済」（`t` から最初の行まで変化がないため）。
3. 期間内に行が1つもなければ、期間内に変化がないので、期間内の日に BOSS のレポートを取り込んだ調査の値（基準の調査）。基準の調査にその SKU がなければ `NULL`。

この方法では、レポートを出力した時刻を知らなくても再現できる。ただし、履歴の期間に基準の調査の日が含まれていること（前提 3）が必要になる。

## 作業範囲

**含む**

- 在庫変動履歴 CSV の読込と検証、再現の計算、調査への保存（休日の調査がなければ作る）
- データ取込画面での取込（内容の確認 → 適用の2段階）
- 調査結果・調査履歴・在庫推移での「履歴から再現」の表示
- 既存の取込・再照合・Amazon 同期と組み合わせたときの扱い
- 上記の PHPUnit・Vitest、操作マニュアル、要件定義書、運用手順の更新

**含まない**

- TQ（フリー在庫・ECストック）の補完
- BOSS からの自動取得（BOSS に API がないため。履歴の出力は手作業）
- 日次在庫CSV・外部公開API への列の追加（前提 5）
- ブラウザでの表示確認（各チケットの完了後に依頼者が行う）

## 前提（推奨案で計画済み。変える場合は該当チケットを修正する）

| # | 論点 | 計画上の扱い | 影響するチケット |
| --- | --- | --- | --- |
| 1 | 再現する時点 | 各日の 9:00（日本時間）。Amazon の取得（9:00）と、平日のレポートを出す時刻（9時前後が多い）にそろえる。値は定数にする | BHR-02, BHR-04 |
| 2 | 補完する日 | 履歴の期間内で、BOSS のレポートを取り込んでいない日。その日の調査がなければ作る（Amazon の取得結果があれば写す）。BOSS のレポートを取り込んだ日は変えない | BHR-04 |
| 3 | 履歴の期間の条件 | 履歴の期間内に、BOSS のレポートを取り込んだ調査日が1日以上あること（基準の調査）。運用では「休日前の最後の出勤日の 0:00 〜 休日明けの出勤日のレポート出力後」を出力する | BHR-02, BHR-04, BHR-08 |
| 4 | 履歴と実際のレポートが合わない SKU | 基準の調査の日について、その日のいずれかの時刻で、履歴から求めた値と保存済みの値が一致するかを SKU・倉庫ごとに確かめる。一致する時刻がない SKU は、補完する日すべてで `NULL`（データなし）にし、確認画面に件数と SKU を出す。ほかの SKU は補完する | BHR-02, BHR-06 |
| 5 | 再現した値の見せ方 | 調査結果・調査履歴・在庫推移で「履歴から再現（9:00時点）」と区別する。日次在庫CSV・外部公開API は値だけを出し、列は足さない（外部公開API仕様書に注記だけ足す） | BHR-07, BHR-08 |
| 6 | あとから BOSS のレポートを取り込んだ日 | 実際のレポートの値で上書きし、「再現」の印を外す | BHR-05 |
| 7 | 履歴ファイルの保存 | 取込ファイルと同じく 30日保存し、期限が来たら `survey-files:prune` で消す。ファイル管理画面には出さない | BHR-03 |
| 8 | 使える人 | データ取込と同じ（編集者・特権管理者） | BHR-04, BHR-06 |
| 9 | 履歴の値がマイナスになる SKU | BOSS のレポートの取込と同じく異常値として扱い、その SKU は `NULL` にして確認画面に出す | BHR-01, BHR-02 |

## 共通の完了条件

- 変更範囲の PHPUnit と `vendor/bin/pint --dirty --format agent` を実行する。画面を変えたチケットは `npm run check` と `npm run build` も通す。
- 在庫数の `NULL`（取込待ち・未取得・データなし）を 0 として扱わない。再現できない値は推測で埋めず `NULL` にする。
- 再現した値は、調査の BOSS の列（`survey_skus.boss_own_stock`、`boss_rfc_stock`）に保存する。調査結果・Excel・在庫推移・日次在庫CSV・外部公開API は、今までどおりこの列から値を作る（別の保存先を足さない）。
- 旧5ファイル調査（`AMAZON_SOURCE_LEGACY_FILE`）は補完の対象にしない。
- 架空のデータでテストを作り、検証に使った実データはリポジトリに入れない。
- 画面の文言・検証メッセージ・コメントは日本語で書く。
