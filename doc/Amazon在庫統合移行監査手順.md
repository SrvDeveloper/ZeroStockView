# Amazon在庫統合の移行前監査

`AMZSYNC-01` の読取り専用監査。アプリケーションの `src/` で実行する。

```bash
php artisan survey:amazon-audit
php artisan survey:amazon-audit --json > /tmp/survey-amazon-audit.json
```

XServerの本番SSHでは、既存の[定期運用手順](Amazon在庫取込の定期運用.md)と同じPHP 8.3 CLI（例: `/usr/bin/php8.3`）で `artisan` を実行する。単なる `php` は古いCLIを指す場合がある。

標準表示には調査種別の件数、Amazon成功取込の日別件数、判定不能・要確認の調査IDを出す。`--json` は全調査について、調査日、分類理由、保存ファイル種別、SKU件数、保存済みAmazon数量の合計、紐づく取込ID・日付、その日の最新成功取込IDを出す。コマンドはDBへの書込みやファイルの削除を行わない。出力には調査IDや在庫数量が含まれるため、結果ファイルをリポジトリや公開ディレクトリに置かない。

## 分類規則

| 判定 | 根拠 | 移行時の扱い |
| --- | --- | --- |
| `legacy_file` | 明示された取得方式が `legacy_file` で旧フラグと矛盾しない。または取得方式が未設定で、旧方式フラグが真かつAmazonファイルの記録がある／他のファイル記録がなく保存済みAmazon数量が正数 | 保存値を維持する |
| `three_file` | SKUが存在し、明示された取得方式が `sp_api` で旧フラグ・ファイルと矛盾しない。または取得方式が未設定で、旧方式フラグが偽かつAmazonファイル記録と正数のAmazon保存値がない | 同日成功取込の再同期候補 |
| `ambiguous` | フラグとファイル・数量の矛盾、未知のファイル種別、SKUなし、旧方式なのにSP-API取込IDあり、旧方式フラグ以外の根拠が不足 | 自動移行しない。ID単位で調査する |

ファイル保持期間を過ぎると `survey_files` の行も削除される。取得方式が未設定で旧方式フラグが真の場合、ファイル記録と正数のAmazon数量がなければ旧5ファイル調査と断定しない。取得方式が未設定で旧方式フラグが偽の場合、Amazonファイルや正数のAmazon保存値が残ると矛盾として止める。明示された `sp_api` 調査は、後日の同期で正数のAmazon数量が保存されても3ファイル調査として扱う。判定不能な履歴を0数量だけで3ファイル調査に分類しない。

監査は、調査の `executed_at` とAmazon取込の `snapshot_date` を東京時間の日付で比べる。日付が違う取込ID、失敗取込ID、当日の最新成功分ではない取込IDを確認事項として出す。日別の最新成功分は `basis_at`、`completed_at`、IDの降順で選ぶ。同日の成功分がなければ3ファイル調査を「取込待ち」と報告する。これらの確認事項だけを理由に旧調査の分類を変更しない。

## 移行前後の照合と復旧

1. 本番のDBと `src/storage/app/private/survey-imports` のバックアップを取得し、復元できる場所・取得時刻・担当者を運用記録に残す。DBのバックアップには `surveys`、`survey_products`、`survey_skus`、`survey_files`、`amazon_inventory_imports`、`amazon_inventory_snapshots` を含める。取込ファイルの保存期限切れはバックアップでも復元できないため、保存されていない履歴は判定不能のまま扱う。
2. スキーマ変更前に監査を実行し、3分類の件数、判定不能ID、日別成功件数、各調査のAmazon数量と紐づく取込IDを保管する。判定不能IDはファイル記録・取込日時・運用記録と突き合わせ、判断結果をID単位で記録する。
3. `AMZSYNC-09` のバックフィルをdry-runで実行し、監査の `three_file` 件数、当日成功分あり／なしの件数、更新予定IDが一致することを確認する。`legacy_file` と `ambiguous` は更新予定に含めない。
4. 適用後に再度監査し、旧5ファイルのSKU別Amazon数量、メモ、ファイル記録が変化していないこと、3ファイル調査の取込IDが同日の最新成功分になったこと、Amazon取得前の数量がNULLであることを照合する。複数の調査日とSKUを抽出し、調査結果・推移・CSV・外部APIの値も突き合わせる。
5. 不一致があれば取込と再同期を止め、変更した調査IDと範囲を特定する。バックアップから復元する場合は、DBと保存ファイルを同じ取得時点の組で戻し、監査結果と旧履歴の数量を再照合してから処理を再開する。

本手順は監査と移行判定の準備であり、バックフィルの実装・本番実行は `AMZSYNC-09` に含める。
