# SP-API 在庫取込チケット

## 確定した方針

- Amazon の自社発送在庫と FBA 出荷可能在庫を SP-API から取得する。
- API 取得結果は既存の5ファイルによる在庫調査とは別の日次履歴に保存する。既存の調査結果を更新しない。
- 手動実行と毎朝9:00（Asia/Tokyo）の自動実行は同じ取込処理を使う。9:00は開始予定時刻であり、レポート生成後の完了時刻ではない。
- 対象品番は保存済み取込設定の対象品番の和集合とし、実行時に商品識別子管理システムから最新の SKU・ASIN 対応を取得する。同じ品番が複数設定にある場合は1回だけ取り込む。
- Amazon 在庫推移には API 履歴を反映する。同日内に API 履歴と手動調査がある場合は、在庫基準日時が新しい結果を採用し、取得元を表示する。API レポートに正確な在庫時刻がない場合は取得完了時刻を基準日時として明示する。BOSS などを含む合算値に異なる時点の数量を混ぜない。
- 過去日付の取得は調査チケットで可否を判定する。現在値を過去の日付として保存しない。

## 実装順

`SPAPI-01 → SPAPI-02 → SPAPI-03 → SPAPI-04` を最初の利用可能な単位とする。`SPAPI-05` と `SPAPI-06` は `SPAPI-03` の後に進められる。`SPAPI-07` は独立した調査として扱う。

## SPAPI-01 レポートと権限の接続確認

**目的:** 現行ファイルの数量と SP-API レポートの数量が一致する取得方法を確定する。

**作業**

- 日本のマーケットプレイスと Far East エンドポイント、アプリの必要ロール、LWA 認証情報とリフレッシュトークンの取得方法を確認する。秘密情報はリポジトリやチケットに記載しない。
- 自社発送の候補 `GET_FLAT_FILE_OPEN_LISTINGS_DATA` と FBA の候補 `GET_FBA_MYI_UNSUPPRESSED_INVENTORY_DATA` を実アカウントで少量確認する。
- `doc/取込データサンプル/` の「在庫商品レポート」「FBA在庫管理レポート」と、ASIN・数量・対象行・ヘッダー・区切り文字・文字コードを照合する。必要なら自社発送レポートの候補を変更する。
- FBA は `afn-fulfillable-quantity` と現行の「Amazon出荷在庫(出荷可)」が同じ値になるか確認する。

**完了条件**

- 使用するレポート種別、必要ロール、数量列、文字コード、照合キー、既存サンプルとの差分をこの文書または別の設計メモに記録している。
- 自社発送・FBA とも取得できる。取得できない場合はロールや認可などの原因と次の対応を記録している。

### 接続確認結果（2026-10-13）

**接続先と認証**

- 日本の Marketplace ID は `A1VC38T7YXB528`、SP-API エンドポイントは `https://sellingpartnerapi-fe.amazon.com`（Far East）。
- LWA リフレッシュトークンからのアクセストークン取得に成功した。認証情報、トークン、署名付き URL、レポート本文はリポジトリに保存していない。
- 実際の API 呼び出しが成功したため、現在のアプリに両レポートを取得できるロールが付与されていることは確認済み。公式仕様上の必要ロールは、自社発送が Inventory and Order Tracking、Pricing、Direct to Consumer Shipping (Restricted)、Product Listing のいずれか、FBA が Pricing または Amazon Fulfillment。

**採用するレポートと列対応**

| 在庫区分 | reportType | 取得結果 | 区切り・文字コード | 照合列 | 数量列 |
| --- | --- | --- | --- | --- | --- |
| Amazon:自社 | `GET_FLAT_FILE_OPEN_LISTINGS_DATA` | 成功（818行） | タブ区切り、UTF-8 BOM あり | `ASIN` | `数量`（英語ヘッダーでは `quantity`） |
| Amazon:FBA | `GET_FBA_MYI_UNSUPPRESSED_INVENTORY_DATA` | 成功（484行） | タブ区切り、SJIS-win、BOM なし | `asin` | `afn-fulfillable-quantity` |

- 互換性を優先して ASIN を照合キーとする。実データでは Amazon の Seller SKU と CrossWalker の SKU コードの表記が異なるため、Seller SKU の文字列一致は要求しない。同一 ASIN の対象 SKU が複数ある場合は設定不備として失敗させる。
- 自社発送は `preferredReportDocumentLocale=ja_JP` を指定できる。FBA に同じ `reportOptions` を渡すと `400 InvalidInput` になるため、FBA は `reportOptions` なしで要求する。

**既存サンプルとの差分**

- 自社発送の既存サンプルはタブ区切り、UTF-8 BOM ありで、API レポートと同じ `出品者SKU`、`ASIN`、`価格`、`数量` を含む。API 側には法人価格と数量割引関連列も含まれる。
- FBA の既存サンプルは CSV、SJIS-win、BOM なし。API レポートはタブ区切り、SJIS-win、BOM なしで、英語ヘッダーを返す。既存の `Amazon出荷在庫(出荷可)` は API の `afn-fulfillable-quantity` に対応する。
- 2026-09-18 の既存サンプルと2026-10-13 の API 現在値を比較した。自社発送は共通 818 ASIN のうち 792 件、FBA は共通 482 ASIN のうち 148 件で数量が一致した。取得日が異なるため、不一致を列対応の問題とは判定しない。

**完了判定と追加確認**

- レポート種別、必要ロール、数量列、文字コード、照合キー、既存サンプルとの差分を記録し、実アカウントで両レポートを取得できたため SPAPI-01 は完了とする。
- 取得日が異なるサンプルでも多数の ASIN で数量一致を確認できたため、採用した数量列は妥当と判定する。本番適用前には、API 取得と同時点の Seller Central レポートで代表 SKU と全体件数を再照合する。この追加確認は SPAPI-02 の着手を妨げない。

## SPAPI-03 Amazon 在庫履歴の保存

**目的:** 取込結果を、既存調査から独立した日次スナップショットとして残す。

**作業**

- 取込実行単位の状態（受付、処理中、成功、失敗）、起動元、開始・完了時刻、件数、失敗理由と、SKU別の自社発送・FBA 数量を保存する。
- 対象 SKU と ASIN の対応を取込開始時に確定する。同一 ASIN、重複行、未照合行、空欄、0、負数の扱いを現行ルールと照合して定義する。対象行が存在しない SKU の 0 補完は、レポート全体が正常に取得・検証できた場合に限る。
- 2種類のレポートそれぞれの取得完了時刻を記録し、表示用の基準日時の決め方を固定する。
- 両レポートの取得と検証が成功したときだけ1件の履歴として確定する。片方の失敗時に 0 在庫や途中結果を保存しない。
- 基準日時と取得元を保存し、再実行で同じ日付の履歴を上書きしない。重複起動は排他制御する。

**完了条件**

- SKU別に両数量、基準日時、取得元を参照できる。
- 失敗時は前回の成功履歴が保持され、取込失敗を画面/APIで判別できる。
- 正常系、行の重複・不正値、対象外 ASIN、片方のレポート失敗、同時起動をテストで確認する。

### 実装・検証結果（2026-10-14）

- 保存済み取込設定の品番を重複除去して CrossWalker から更新し、有効 SKU と ASIN の対応を取得開始時に固定する。ASIN 未設定の SKU は Amazon 在庫の履歴から除外し、0 在庫として保存しない。ASIN 付きの有効 SKU が1件もない場合と、SKU・ASIN の重複は失敗とする。
- 対象外 ASIN は無視し、対象 ASIN の重複行・負数・不正数値・上限超過は失敗とする。Amazon の Seller SKU と CrossWalker の SKU コードは表記が異なるため、ASIN でのみ照合する。FBA Inventory API への代替時は、同一 ASIN の複数 Seller SKU 行を合算して1件として扱う。空欄と 0、正常な両取得元に存在しない対象 SKU は 0 として保存する。識別子のないレポート全体は失敗とする。
- 自社発送と FBA の取得完了時刻を別々に保存する。基準日時は両者の遅い方の取得完了時刻とし、東京時間の日付で履歴を分類する。取得元は `sp_api`、起動元は `manual` または `scheduled` として保持する。同じ日付の再実行は別の履歴として追加する。
- 実行状態は受付・処理中・成功・失敗を保持する。排他キーの一意制約で重複受付を防ぎ、2時間を超えた未完了実行を失敗として解放する。2レポートの取得と検証が揃った時だけ SKU 履歴をトランザクションで保存する。
- 認証済みの `GET /api/amazon-inventory-imports` と `GET /api/amazon-inventory-imports/{id}` で実行状態、失敗理由、SKU別数量を参照できる。画面からの起動と表示は SPAPI-04 で追加する。
- 集中テストで最新 SKU・ASIN 対応、対象品番の重複、ゼロ補完、対象外 ASIN、重複・不正値、片方のレポート失敗、同時起動、同日再実行、認証付き参照を確認した。`composer test` は48件通過。`npm run check` は既存の `BaseTextarea.vue` の整形警告と `eslint.config.js` 欠落で停止した。
- 2026-10-14 の実行で、`spc-006` と `spc-007` に ASIN 空欄の有効 SKU が各4件あることを確認した。両品番には ASIN 付き SKU もあるため、空欄の8件だけを API 履歴から除外する扱いに修正した。ASIN がない SKU の数量を0と断定せず、照合可能な SKU のみを保存する。集中テストと `composer test` 52件が通過した。

## SPAPI-05 毎朝9時の自動実行と運用

**目的:** 手動操作なしで毎朝の在庫履歴を蓄積する。

**作業**

- Laravel Scheduler に Asia/Tokyo の毎日9:00起動を登録し、SPAPI-03 と同じジョブを投入する。
- 自動・手動の同時起動を防ぐ。失敗を履歴とアプリケーションログで確認できるようにする。
- 運用手順に、XServerのCronから5分ごとに起動する Laravel Scheduler、1件の処理後に終了するキューワーカー、失敗時の再実行方法を記載する。

**完了条件**

- スケジュール一覧に9:00のジョブが現れ、指定時刻に1回だけ投入される。
- ワーカー停止や Amazon 側の失敗時に、成功したように表示されない。
- XServerでCronの設定とScheduler・ワーカーの実行を確認できる。

### 実装・検証結果（2026-10-14）

- Laravel Scheduler に Asia/Tokyo の毎日9:00起動を登録し、手動実行と同じ専用キューに投入する。同じ東京日付の定期取込は再投入せず、手動実行中も DB の排他キーで重複を防ぐ。
- 5分ごとの期限切れ確認を登録した。ワーカー停止などで2時間を超えた取込は失敗履歴に変更し、取込処理とジョブの失敗はアプリケーションログにも記録する。
- `php artisan schedule:list` に9:00起動と5分ごとの期限切れ確認・ワーカー起動が表示されること、集中テスト5件で投入先・同日重複・手動実行との排他・期限切れ失敗・ジョブがある場合のみのワーカー起動を確認した。
- XServerレンタルサーバーに合わせ、5分ごとの `schedule:run` から Laravel Scheduler を起動し、ジョブがある場合だけ `queue:work --stop-when-empty --max-jobs=1` を実行する構成に変更した。9:00の定期投入は維持し、手動実行は最大5分待つ。常駐プロセスを前提としない。設定・確認手順は [Amazon在庫取込の定期運用](Amazon在庫取込の定期運用.md) に記載した。XServerでのCron設定と9:00の実行確認は未実施。

## SPAPI-06 在庫推移への反映

**目的:** 蓄積した Amazon 在庫を日付・SKUごとに見られるようにする。

**作業**

- 在庫推移の Amazon 区分に API 履歴を追加し、同日の複数結果は基準日時が最新のものを選ぶ。手動調査と競合する場合も同じ基準を使う。
- 数量の取得元と基準日時を表示する。API 履歴だけがある品番・日付も選択できるようにする。
- BOSS・フリー在庫・ECストックと合算する表示、および既存の日次全倉庫 CSV は、異なる取得時刻の数量を暗黙に混ぜない。必要な場合は取得元別の出力を追加する。

**完了条件**

- API 履歴のみの日、手動調査のみの日、両方ある日の Amazon 在庫数と取得元が正しい。
- 他の在庫区分と既存調査の履歴表示が変わらない。

**実装メモ（2026-10-14）**

- Amazon区分では品番・日付ごとに成功したSP-API取込と手動調査を比較し、基準日時が新しい結果を採用する。同日の複数取込も基準日時順に選ぶ。
- 取得元と基準日時は在庫推移画面の日別一覧に日本時間で表示する。SP-API履歴だけの品番も検索・表示できる。
- モール全体・総数を含む他区分と既存の日次全倉庫CSVは手動調査のみを使用する。APIだけの品番では品番指定の手動調査CSVを無効化する。
- 朝の取込日が前日に変わることを防ぐため、`snapshot_date`を日本時間の暦日として読み書きする。本番での表示確認は後日行う。
