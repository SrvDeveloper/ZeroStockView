# ゼロ在庫照会システム「ZeroStockView」要件定義書

- 正式名称：ゼロ在庫照会システム
- システム名：ZeroStockView
- 読み方：ゼロストックビュー

[要件概要.md](要件概要.md) と、その後の決定事項をもとに、開発に必要な機能・操作・取込ルール・データの扱いをまとめる。要件概要と異なる箇所は、その後の決定事項を反映した本書の内容を優先する。

## 1. システムの目的と方針

Amazon在庫をSP-APIから取得し、BOSSとターコイズ（TQ）の在庫ファイルを取り込み、指定した品番・SKUの在庫数を確認する社内システム。

1人の開発者が作る簡素なシステムとし、使いやすさと実装の簡便さを重視する。画面の配置や操作の細部はフロントエンド構築時に調整する。

- 複数の利用者が1つの共通アカウントを使用する。設定・調査履歴・メモ・ファイルはすべて共有する。
- 商品マスタ管理機能は持たない。本システムで管理するのは、調査結果の絞り込みと表示順に使う品番グループの品番の選択・削除・並び順のみとする。
- 品番・SKU・ブランド・カテゴリ・識別子は、商品識別子管理システムからAPIで取得・保持する。外部マスタへの書込みは行わない。
- ユーザー管理、権限管理、承認、パスワード失念時の再設定、ファイルプレビュー、バックアップ機能は作らない。
- 詳細な非機能要件や運用管理機能は設けない。

本書でいう「1回の調査」は、BOSS・ECストック・フリー在庫の1～3種類のファイルから対象品番（商品識別子管理システムで有効な全品番）に属する各SKUの在庫数をまとめ、1件の結果として保存する処理を指す。Amazon在庫は調査日と同じ日本時間の日付に取得成功した最新のSP-API結果を各SKUに保存する。取得前は未確定として保存し、その日の取得成功後に更新する。ファイル取込がまだない日にAmazon在庫の取得が成功した場合は、Amazon在庫だけの調査を作成し、BOSS・ECストック・フリー在庫は取込待ちとする。「在庫調査結果」と「在庫調査レポート」は同じ内容を指し、画面とExcelで参照できる。

## 2. 利用の流れ

1. ログインし、データ取込画面を開く。
2. 必要に応じて、絞り込みと表示順に使う品番グループを設定する。取込の対象は品番グループに関係なく、商品識別子管理システムで有効な全品番とする。
3. BOSSとTQから出力した対象ファイルを1～3件添付する。
4. 取込・調査を実行する。開始前に商品情報をAPIで最新化する。
5. 調査結果を確認し、絞込・メモ入力・Excel出力を行う。
6. 過去の結果は調査履歴から参照する。

ログイン後はメニューから、データ取込・品番グループ・ダッシュボード・調査履歴・ファイル管理・パスワード変更へ移動できる。調査完了時は今回の結果を開き、履歴からは選んだ調査の結果を開く。ダッシュボードは最新の結果を参照する入口とする。

## 3. 画面と機能

| 画面 | 機能 |
| --- | --- |
| ログイン | ログインID・パスワードで認証する。成功後はデータ取込画面へ移動する |
| データ取込 | BOSS・ECストック・フリー在庫のファイルを1～3件まとめて添付し、内容から種類を判定して取込・調査を実行する |
| 品番グループ | 調査結果の絞り込みと表示順に使う品番の選択・削除・並び順を設定する。取込の対象には影響しない |
| ダッシュボード | 最新の在庫調査結果を表示する |
| 在庫調査履歴 | 調査結果を新しい順に一覧表示し、結果の参照・削除を行う |
| 在庫調査結果 | 品番・SKU別の在庫数を表示し、絞込・メモ入力・Excel出力を行う |
| ファイル管理 | 調査ごとに取込ファイルを一覧表示し、ダウンロード・削除を行う |
| 在庫推移（品番一覧） | 全品番の最新在庫・前週比・期間の推移・SKUの状況・欠品を一覧で表示し、絞込・並び替え・日次在庫CSVの出力を行う |
| 在庫推移（品番の詳細） | 1品番の倉庫別の日別在庫、SKU別のヒートマップ、カラー × サイズの在庫、欠品中のSKUを表示し、その品番の日次在庫CSVを出力する |
| パスワード変更 | 共通アカウントのパスワードを変更する |

### ログイン・パスワード変更

- 初回アカウントはターミナルから作成できること。
- ログインID・パスワードが一致したらデータ取込画面を開く。一致しなければログイン画面にエラーを表示する。
- 調査結果やファイルなどの利用にはログインを必要とする。ログアウトするとログイン画面に戻る。
- パスワードには半角英数字記号を使用でき、12文字以上とする。文字種の組合せなど、追加の条件は設けない。
- パスワード変更を保存したら、次回以降のログインでは変更後のパスワードを使用する。変更は共通アカウントに反映される。

### 品番グループ画面

- 商品識別子管理システムに登録されている品番から、グループごとに1～50件選択する。同じ品番を複数グループに登録できる。
- グループ内の品番を一覧表示し、追加・対象からの削除・並び順変更を行える。同じグループ内では品番を重複登録しない。
- 保存したグループの所属は、次の調査から結果の絞り込みと表示順に使う。品番グループが1件もなくても、取込・調査・再照合は実行できる。
- 選択した品番に紐づくブランド、カテゴリ、各SKU、ASIN、TQ品番、TQカラーNo、TQサイズを取得・保持する。
- 品番をグループに追加するときに、その品番の商品情報を取得する。毎回の取込開始前には、有効な全品番の一覧と商品情報を取得する。
- API取得に失敗した場合は調査を進めず、利用者に再試行を求める。
- グループから品番を削除しても、取込の対象からは外れない。外部の商品マスタは削除しない。
- 品番・SKUや取得した商品情報そのものを編集する画面は設けない。設定変更は次回以降の調査に反映し、保存済みの過去結果は変更しない。

### データ取込画面

- BOSS・ECストック・フリー在庫のCSVを1～3件まとめて添付する。種類別の添付欄とAmazonファイルの添付欄は設けない。ファイル名ではなく、CSVのヘッダーから種類を判定する。
- 参照選択とドラッグアンドドロップに対応し、選択したファイル名を一覧表示する。実行前にファイルを追加・削除できる。
- 1件以上のファイルが添付された状態で実行できる（品番グループの設定は不要）。取込後は全対象品番を表示し、結果画面で品番グループを絞り込める。
- 実行中であることを表示し、同じ画面での実行ボタンの連打を防ぐ。
- 正常に完了したら結果と使用ファイルを調査に紐づけて保存し、その結果画面へ移動する。
- 取込に失敗したら原因を表示する。ファイルの修正・差替え、またはAPI取得の再試行後に実行できる。
- BOSSの在庫変動履歴のCSVを1件選ぶと、休日のBOSS在庫の補完内容（基準の調査、補完する日、データなしになるSKUとその理由、補完できない日）を確認でき、確認したうえで補完を実行できる（4章「BOSS:自社／BOSS:RFC の休日補完」）。

### ダッシュボード・在庫調査結果画面

- ダッシュボードには、保存されている調査のうち最新の結果を表示する。まだ調査がなければ未実施と表示し、データ取込画面へ進めるようにする。
- 結果画面では調査日時を示し、どの調査を見ているか分かるようにする。
- 品番ごとにSKUと在庫数を表示し、絞込・メモの保存・Excel出力ができる。Amazon在庫の取得元と基準日時も示す。詳しい表示内容は5章に定める。
- 履歴から開いた結果でも、その調査のメモを編集し、Excelを出力できる。

### 在庫調査履歴画面

- 調査日時が新しい順に一覧表示し、各履歴から結果を開ける。
- 任意の履歴を削除できる。削除後は一覧から取り除く。
- 最新の履歴を削除した場合、ダッシュボードには残っている履歴のうち最新の結果を表示する。
- 保持件数と関連データの削除は6章に定める。

### ファイル管理画面

- 調査日時ごとにファイルをまとめ、ファイルの種類・名前・アップロード日時を確認できる。
- 個別ダウンロード・削除と、調査単位のZIPダウンロード・一括削除を行える。
- 削除済みのファイルはダウンロード対象にしない。ファイル内容のプレビューは設けない。
- ファイルの保存期間と削除時の結果への影響は6章に定める。

### 在庫推移画面

- 在庫推移は「品番一覧」と「品番の詳細」の2画面とする。メニューからは品番一覧を開き、品番を選ぶと詳細を開く。
- 在庫区分（モール全体・Amazon・BOSS・フリー・ストック・総数）と表示期間（2週間・1か月・3か月は最新の調査日までの期間、期間指定は最大365日）を選べる。条件は URL に持たせ、一覧と詳細を行き来しても引き継ぐ。
- 品番一覧は、品番グループ・ブランド・品番/SKU/ASIN の検索と、注目する品番（欠品SKUあり・欠品が増えた・在庫が10%以上減った・30日以上の欠品）で絞り込める。初期の並び順は欠品SKUの多い順とする。
- 品番の詳細では、前後の品番へ移れる。前後の順番は、一覧から開いたときはその一覧の絞込と並び順に従い、URL を直接開いたときは品番コード順とする。
- 集計の規則は5章の「在庫推移」に定める。

## 4. 在庫データの取込

### 共通ルール

- 下表の3種類から1種類以上のファイルが添付されたら、取込・調査を実行できる。各種類は最大1件とし、判定不能・複数種類に一致・同じ種類の重複はエラーにする。
- 1行目をヘッダーとして扱い、商品識別子管理システムで有効な全品番の、有効なSKUに紐づく行だけを取り込む。有効なSKUが1件もない品番は対象にしない。同じ品番が複数グループに属していても在庫は1件として保存する（2026-10-23 に、全品番グループに登録された品番の和集合から変更）。
- 品番・SKU・TQの識別子は文字列として照合し、先頭ゼロを保持する。
- 数量が空欄の行は取込対象から除外する。数値として取得できる行を使用し、マイナス値は異常値としてエラーにする。
- 取込済みファイル内で該当SKUの行がない場合、ECストック・フリー在庫は0として扱う。BOSSは在庫0のSKUも含めて全SKUを出力するため、ファイルに載っていないSKUは在庫不明（null、画面では「—」）として扱い、0と区別する。未添付の種類は取込待ち（null）として扱い、0と区別する。同じ日本時間の日付の調査履歴は1件とし、初回取込（ファイル取込より先にAmazon在庫の取得が成功した日はその時点）で作成し、追加取込では添付した種類のファイルを更新して再集計する。調査時点の品番とグループの所属を保存し、履歴と結果は選択したグループの品番に絞って表示できる。ASINが登録されたSKUでSP-API在庫が存在しない場合や対応するスナップショットがない場合、Amazon在庫は未取得として扱い、0と区別する。ASINがないSKUはAmazon取得の対象外とする。
- ECストックは同じSKUの対象行を合算する。それ以外は同じ在庫区分・SKUへの重複をエラーとする。BOSSの自社倉庫行とRFC倉庫行は別区分なので重複には当たらない。
- ファイル検証は、読み込めること、必要列があること、上記の数量・重複チェックなど、取込に必要な最小限にする。
- 提示サンプルに合わせ、CSVはCP932を読み込めること。

必要な列はヘッダー名で読み取り、記載のない列は数量の計算に使用しない。CSVの引用符付きの値も読み取れるものとする。TQの照合は、TQ品番・TQカラーNo・TQサイズの3項目がすべて一致することを条件とする。

### 取込処理と結果の保存

1. 商品識別子管理システムから有効な全品番と商品情報を取得し、手元の商品情報を最新化する。一覧から無くなった品番は無効にして対象から外す。一覧が空の場合は、全品番を無効にせずエラーとする。
2. 対象品番に属する有効な全SKUについて、添付済みのECストック・フリー在庫は在庫数0、BOSSと未添付の種類はnullで用意する。
3. 添付ファイルのヘッダーから種類を判定し、対象SKUに対応する行を抽出して以下のファイル別ルールで数量を反映する。対象外の行は取り込まない。
4. ECストックは対象行の数量を合算する。他区分は重複がないことを確認する。
5. 正常に処理できた結果を、その日の調査に商品情報・品番グループの所属・使用ファイルとともに保存する。初回は調査を作成し、同日の追加取込では更新する。同じ日本時間の日付に成功したSP-API取込結果があれば、その最新の数量をSKUごとに保存する。

取込済みの種類でファイルにないSKUの数量は、ECストック・フリー在庫は0、BOSSはnull（在庫不明）とする。同日に先に取り込んだ別種類のファイルは引き継ぎ、同じ種類のファイルを再添付した場合は差し替えて再集計する。Amazon在庫が未取得のSKUは `null` とし、確認済みの0在庫と区別する。同日のSP-API取込が後で成功した場合は調査内のAmazon数量を更新し、同日に複数回成功した場合は最新の成功分を採用する。ファイル取込より先にSP-API取込が成功した日は、その時点で手元の商品情報からAmazon在庫だけの調査を作成し、後のファイル取込では同じ調査を更新する（初回取込日時とメモは変えない）。

### 除外・エラーの扱い

| 状況 | 処理 |
| --- | --- |
| 対象品番のSKUに一致しない行 | 取り込まない |
| 数量が空欄の行 | その行を除外する |
| ECストック・フリー在庫の数量が0 | 正数の取込条件に該当しないため除外する。結果の在庫数は0のまま |
| 対象行の数量がマイナス | 異常値としてエラーを表示する |
| ECストック以外で同一SKU・同一区分の取込行が重複 | エラーを表示する |
| ファイルが読めない・必要列がない | 対象ファイルと理由を表示する |
| 内容から種類を判定できない・同じ種類が複数ある | 対象ファイルと理由を表示し、調査を保存しない |
| API取得失敗 | 利用者に再試行を求める |

数値判定は各ファイルで指定した数量列に対して行う。マイナス値は、TQの「1以上」という条件で単に除外する前に異常として検出する。

エラーで完了できなかった調査は結果・履歴として保存せず、途中の数量でその日の結果を上書きしない。正常なファイルで取込をやり直した場合は、その日の調査を更新する。未取得を0とする扱いは、ファイルを正常に処理した結果に適用し、API失敗やファイル読込失敗を0在庫の正常結果として扱わない。

### 取込元と在庫区分

| ファイル | 形式 | 保存する在庫区分 |
| --- | --- | --- |
| 倉庫毎の在庫数レポート | CSV | BOSS:自社、BOSS:RFC |
| KEEP一覧表 | CSV | ECストック |
| 在庫一覧照会表 | CSV | フリー在庫 |

### Amazon:自社／Amazon:FBA

- Amazon在庫はSP-APIの定期取得または手動取得の結果を使用し、ファイル取込は行わない。取得の対象は、取得開始時に商品識別子管理システムで有効な全品番の、有効なSKUとする。
- 調査日と同じ日本時間の日付に成功した最新の取込結果をSKUコードで照合する。取得が調査より後でも、その日の調査SKUに数量を保存する。対応するSKUがない場合は未取得とする。ASINが登録されていないSKUは対象外とし、一部未取得の判定から除く。対象外SKUのAmazon数量は空欄のままとし、総在庫への加算値は0とする。取込結果にASINがあるのに調査履歴側で欠けている場合は、取込結果のASINを履歴に補う。
- 調査履歴には取込待ち・取込済み・一部SKU未取得の状態とAmazon基準日時を示す。旧5ファイル調査のAmazon在庫は保存済みの数量を引き続き表示する。

### BOSS:自社／BOSS:RFC

- BOSSの商品・在庫一覧画面から出力した「倉庫毎の在庫数レポート」を使用する。
- 必須列は `倉庫`、`SKUコード`、`実在庫 (倉庫毎)`、`引当済 (倉庫毎)`。
- SKUコードが対象SKUと一致する行を取り込む。
- 倉庫が `自社倉庫` の行は `BOSS:自社`、`RFC倉庫` の行は `BOSS:RFC` に保存する。
- `実在庫 (倉庫毎) - 引当済 (倉庫毎)` を各倉庫の在庫数として扱い、自社・RFCの両方の行を取り込む。
- BOSSは在庫0のSKUも含めて全SKUを出力する。ファイルに載っていないSKUは自社・RFCとも在庫不明（null）とし、載っているSKUで片方の倉庫の行がない場合は、その倉庫を0とする。

### BOSS:自社／BOSS:RFC の休日補完

BOSSのレポートは手作業で出力するため、出勤しない休日はBOSS在庫が歯抜けになる。BOSSから出力した「在庫変動履歴」で、休日のBOSS在庫を再現して調査に保存できる。補完するのはBOSS（自社倉庫・RFC倉庫）だけで、ECストック・フリー在庫は補完しない。計画と検証結果は `docs/BOSS在庫の休日補完/README.md`、運用は `doc/BOSS在庫の休日補完の運用.md` を参照する。

- 必須列は `処理日時`、`処理種別`、`処理番号`、`SKUコード`、`倉庫`、`変動前実在庫`、`変動後実在庫`、`変動前引当済`、`変動後引当済`。`自社倉庫`・`RFC倉庫` 以外の倉庫の行は読み飛ばす。`変動後実在庫 - 変動後引当済` の列があれば、計算と一致するかを確かめる。
- 在庫数はBOSSのレポートと同じく「実在庫 − 引当済」とする。同じSKU・倉庫の行を処理日時の順に並べ、同じ秒の行は「変動前」が直前の行の「変動後」とつながる順にする。
- 再現する時点は各日の9:00（日本時間）とする。ある時刻のSKU・倉庫の在庫は、その時刻以前の最後の行の変動後、なければその時刻より後の最初の行の変動前とする。期間内に行がなければ、期間内にBOSSのレポートを取り込んだ調査（基準の調査）の値とし、基準の調査にもなければデータなし（null）とする。
- 履歴の期間に、BOSSのレポートを取り込んだ日が1日以上含まれていなければ補完しない。レポートを出力した時刻は、保存済みの値と履歴の値が最も多く一致する時刻から推定し、それが履歴の最初の行より前の基準の調査は使わない。
- 基準の調査の日に、どの時刻でも保存済みの値と履歴の値が一致しないSKU・倉庫は、補完する日すべてでデータなし（null）にし、確認の表示に件数とSKUを出す。履歴のつながりが9:00をまたいで切れているSKU・倉庫、再現した値がマイナスになるSKU・倉庫もデータなしにする。推測で値を埋めない。
- 補完する日は、履歴の期間内で、その日の調査がない日と、BOSSのレポートを取り込んでいない日（前回の補完のやり直しを含む）とする。BOSSのレポートを取り込んだ日と、旧5ファイル調査の日は変えない。その日の調査がなければ、9:00を初回取込日時として調査を作り、その日のAmazon在庫があれば反映する。
- 補完した日に、あとからBOSSのレポートを取り込んだときは、レポートの値で上書きし、再現の印を外す。KEEP一覧表・在庫一覧照会表だけを取り込んだときは、再現した値を残す。再照合では、補完に使った在庫変動履歴で再現し直し、履歴の保存期限を過ぎていれば再照合前の値を残す。
- 補完できるのは、データ取込と同じく編集者・特権管理者とする。

### ECストック

- TQの在庫管理で、得意先を `59` に絞って出力した「KEEP一覧表」を使用する。
- 使用列は `品番`、`カラーNo`、`サイズ`、`キープ残数`。
- 品番・カラーNo・サイズが、対象SKUのTQ品番・TQカラーNo・TQサイズに一致し、キープ残数が1以上の行を取り込む。
- 同じSKUの対象行が複数あればキープ残数を合算し、`ECストック` に保存する。

### フリー在庫

- TQの在庫管理で、倉庫を `01` に絞り、ゼロ在庫出力の「出力する」のチェックを外して出力した「在庫一覧照会表」を使用する。
- 使用列は `品番`、`カラーNo`、`サイズ`、`可能在庫数`。サイズ列名は `サイズ` と `ｻｲｽﾞ` のどちらも受け付ける。
- 品番・カラーNo・サイズが、対象SKUのTQ品番・TQカラーNo・TQサイズに一致し、可能在庫数が1以上の行を取り込む。
- `可能在庫数` を対応するSKUの `フリー在庫` に保存する。

TQの得意先・倉庫などの出力条件は、利用者が元システムで設定する。

## 5. 調査結果・絞込・メモ・Excel出力

### 在庫数の表示

- 品番グループを選択した場合は、そのグループに属する品番を設定順に表示し、品番ごとにSKUをまとめる。「すべて」では保存済みの全対象品番を表示する。どの品番グループにも入っていない品番は「グループなし」としてまとめ、グループの選択肢の最後に示す。
- 新しい3ファイル調査では、Amazonが取込待ちでもAmazon欄を表示する。Amazonは自社とFBAの合算値、BOSSは自社とRFCの合算値を表示し、フリー在庫、ECストックと合わせた4区分で表示する。Amazon・BOSSの内訳は通常時には表示しない。
- Ctrlキーを押しながらAmazonまたはBOSSの合算値に約0.5秒マウスホバーすると、Amazonは自社・FBA、BOSSは自社・RFCの内訳を表示する。Ctrlキーを離すと内訳を非表示にする。
- BOSS在庫を在庫変動履歴から再現した調査では、調査結果画面の基準日時の並びに「BOSS: 履歴から再現（9:00時点）」を示し、BOSSの列の見出しに印を付ける。調査履歴のカレンダーには「BOSS 再現」の印を付け、在庫推移の倉庫別のグラフでは、ツールチップのBOSSの行に「（履歴から再現）」を添える。数値の表示は変えない。日次在庫CSVと外部公開APIは、再現した値と実際の値を区別しない。
- 在庫数がすべて0のSKUも、絞込前の結果には表示する。Amazon基準日時を示し、取込待ち・未取得・BOSSのデータなし（ファイルに載っていないSKU）の値は「—」で示す。確定した0在庫は「0」で示す。
- 4区分の在庫がすべて確定したSKUでは在庫総数を表示する。未取込・未取得の区分があるSKUでは在庫総数を「—」とし、部分合計を表示しない。Amazonと他区分の基準日時は画面にそれぞれ示す。旧5ファイル調査の総数は従来どおり表示する。
- 開いている調査結果は30秒ごとにAmazon在庫を再取得し、手動でも再読込できる。調査履歴と在庫推移も再読込できる。在庫推移は数量のグラフ・SKU別のヒートマップ・SKU別サマリーを表示し、Amazon在庫の取得元一覧は表示しない。
- 数量は取込結果を参照するものとし、画面での在庫数の直接編集は行わない。
- Amazon・BOSSの合算値が1以上5以下の場合は、在庫僅少の警告として薄い黄色の背景とオレンジ色の文字で表示する。0の場合は既存のゼロ在庫表示を優先する。フリー在庫・ECストックには在庫僅少の警告色を適用しない。

### 絞込

- 調査結果は品番グループ、ブランド・カテゴリの選択、品番・SKU・ASINの入力で絞り込める。調査履歴では調査期間で絞り込み、各調査に含まれる全品番数・SKU数を表示する。
- 次の在庫条件をボタンで選択できる。複数条件を同時選択でき、条件同士の結合方法をANDまたはORから選択する。初期値はANDとする。Amazon在庫がない調査ではAmazon条件を表示せず、SKU別のAmazon未取得値はAmazon条件に一致させない。

| 絞込条件 | 判定 |
| --- | --- |
| Amazon在庫ゼロ | Amazon:自社とAmazon:FBAが両方0 |
| BOSS在庫ゼロ | BOSS:自社とBOSS:RFCが両方0 |
| フリー在庫ゼロ | フリー在庫が0 |
| ECストック在庫ゼロ | ECストックが0 |
| Amazon在庫あり | Amazon:自社とAmazon:FBAの合算値が1以上 |
| BOSS在庫あり | BOSS:自社とBOSS:RFCの合算値が1以上 |
| フリー在庫あり | フリー在庫が0より大きい |
| ECストック在庫あり | ECストックが0より大きい |

- 絞込はSKUごとに判定し、該当SKUを品番ごとにまとめて表示する。該当SKUのない品番は表示しない。
- SKU・ASINの入力で一致した行は青系でハイライトし、在庫僅少を示す黄色・オレンジの警告表示と区別する。
- 調査結果の行にマウスホバーした場合は、SKUセルだけをごく薄いslate色で強調する。在庫セルの背景色は変更しない。
- 例えば「Amazon在庫ゼロ」と「フリー在庫あり」をANDで組み合わせると両方を満たすSKU、ORで組み合わせるとどちらか一方以上を満たすSKUを表示する。
- 条件を解除すれば全件表示に戻る。絞込は表示だけに適用し、保存済みの結果やメモは変更しない。
- 該当するSKUがない場合は0件と表示する。相反する条件の同時選択でも、AND判定の結果が0件になる扱いとする。

### 再照合

- 調査結果画面から保存済みのファイルを使って、商品識別子管理システムで有効な全品番を再照合できる。再照合後の初期表示に使う品番グループを選べる（任意。選ばない場合はすべてのグループを表示する）。
- 再照合は元の調査日と同じ履歴を更新し、その日と同日の最新のSP-API結果を各SKUに反映する。残っているファイルが1種類以上あれば実行できる。ただし、Amazon在庫をファイルで取り込んだ旧5ファイル調査と取得方式を確定できない調査は、保存済みのAmazon在庫を守るため再照合できない（画面ではボタンを無効にして理由を示し、APIでも受け付けない）。
- 再照合に使うファイルが削除済み・期限切れ・実体なしの場合は実行を拒否する。
- 再照合では、使ったファイルのアップロード日時と保存期限を元のまま引き継ぎ、保存期限を延ばさない。

### メモ

- 品番ごとのメモとSKUごとのメモを分けて入力・保存できる。
- メモは調査単位で保持し、同じ調査を開き直したときに保存内容を表示する。
- 同じ品番・SKUでも別の調査のメモには影響しない。新しい調査に前回のメモを自動で引き継がない。
- 共通アカウントのため、保存したメモは利用者全員が参照・編集できる。
- メモは入力欄からフォーカスを外したときに保存する。日本語IMEの変換中や入力途中には保存せず、編集中の文字列を保存値で上書きしない。保存できたことが分かる表示を行う。

### Excel出力

- 調査結果をExcel（`.xlsx`）で出力でき、品番メモ・SKUメモも含める。
- 品番・SKUと利用できる在庫区分の数量を対応付け、どの品番・SKUのメモか分かる形で出力する。新しい3ファイル調査にAmazon在庫がある場合は取得元と基準日時も出力する。BOSS在庫を在庫変動履歴から再現した調査では、BOSSの取得元（在庫変動履歴から再現）と基準日時（9:00）の列も出力する。
- 出力する数量とメモは対象調査の保存値とする。Amazon未確定値は0に変換しない。出力時にAPI取得や再集計は行わない。
- Excelは `出力データ/YYYYMMDDHHii_在庫調査結果.xlsx` を参考にする。
- シート構成・メモ配置・ファイル名の細部、全件と絞込結果の出力操作は、画面側の操作と合わせて実装時に調整する。

### 在庫推移

- 在庫推移は保存済みの調査（`survey_skus`）を日ごとに集計して表示する。同じ日に調査が複数ある場合は、品番ごとにその日の最後の調査を使う。日次在庫CSV・外部公開APIと、同じ日の同じ品番の数値を食い違わせない。
- 在庫区分の数量の決め方は日次在庫CSVと同じとする。SP-API の調査で ASIN のない SKU は Amazon を0とし、Amazon の区分では Amazon 取得の対象外の SKU を除く。
- 取込待ち・未取得・データなしの在庫は未確定とし、0として扱わない。未確定を含む合計は出さずに「—」とする。欠品は在庫が0と確定したものだけを数える。
- 前週比は、最新の調査日とその7日前の調査を比べる。7日前に調査がなければ、それより前で最も近い調査（14日前まで）と比べる。どちらかが未確定のとき、比べる調査がないとき、比べる日の在庫が0のときは「—」とする。
- 連続欠品日数は、最後に在庫（1以上）があった日の後で最初に在庫0と確定した日を欠品の始まりとし、その日から最新の調査日までの日数とする。始まりの前の調査のない日・未確定の日は欠品に数えず、始まったあとの調査のない日・未確定の日では欠品が途切れないとみなす。品番一覧では表示期間に関係なく最新の調査日から最大90日さかのぼって数え、30日以上を長期の欠品とする。品番の詳細では表示期間の中で数え、期間内に在庫のあった日がなければ「◯日目以上」と示す。
- 品番一覧の品番グループは、期間内で最新の調査に保存された所属を使う（調査結果画面と同じ）。表示期間に調査がある品番は、CrossWalker で無効になっていても一覧に出す。
- 品番の詳細のヒートマップは1行1SKU・1マス1日とし、在庫数を固定の段階（0、1〜4、5〜9、10〜19、20〜39、40以上）で塗り分け、未確定と調査のない日を区別して示す。色だけに頼らないよう、数値の表（SKU別サマリー）も開けるようにする。
- カラー × サイズの在庫は最新の調査日の在庫を示し、カラーは TQ のカラー番号で表示する。

## 6. 履歴・ファイルの管理

### 調査履歴

- 調査履歴を新しい順に表示する。
- 調査単位で最大500件を保持し、501件目を保存したら最古（調査日が最も古い）の履歴を物理削除する（2026-10-21 に100件から変更。調査は1日1件なので約1年4か月分）。
- 利用者が任意の履歴を物理削除できる。
- 履歴を削除した場合は、その調査結果・メモ・取込ファイルも削除する。

### 取込ファイル

- CSVの取込ファイルを調査ごとにまとめて一覧表示する。旧調査のTXTファイルも引き続き参照できる。内容のプレビューは不要。
- ファイルを個別にダウンロード・削除できる。
- 調査ごとのファイル一式をZIPでダウンロードでき、一括削除もできる。
- アップロード日時から30日を経過したファイルは自動削除する。
- SP-APIで取得したSKU別のAmazon在庫（スナップショット）は、調査にAmazon在庫を写すためだけに使う。取込の対象日から30日を過ぎたら自動削除する（取込ファイルより後に消える）。調査に保存したAmazon在庫は残る。
- ファイルのみを削除した場合、調査結果とメモは残す。
- BOSSの在庫変動履歴のファイルも、アップロードから30日で自動削除する。ファイル管理画面には出さない。ファイルを削除したあとも取込記録は残し、どの日をどの履歴で補完したかを確かめられるようにする。

### 削除の関係

| 操作・条件 | 調査結果とメモ | 取込ファイル |
| --- | --- | --- |
| 履歴を手動削除 | 対象の調査を削除 | 紐づくファイルを削除 |
| 501件目の調査を保存 | 最古の調査を削除 | 最古の調査に紐づくファイルを削除 |
| ファイルを個別・一括削除 | 残す | 指定したファイルを削除 |
| アップロードから30日経過 | 残す | 期限を経過したファイルを自動削除 |

履歴の500件とファイルの30日は別の条件として扱う。ファイルがなくなった過去の調査でも、保存済みの結果の閲覧・メモ編集・Excel出力はできる。

## 7. 保存するデータと更新の範囲

実装では、次の内容を保存できればよい。テーブルの分け方などの内部構成は開発時に決める。

| 保存する内容 | 用途・更新のタイミング |
| --- | --- |
| 共通アカウント | ログインに使用。初回はターミナルで作成し、パスワード変更時に更新する |
| 品番グループの品番と並び順 | 次回の調査から、結果の絞り込みと表示順に使用。品番グループを保存したときに更新する |
| APIで取得した商品情報 | 品番の有効・無効と、品番に紐づくブランド・カテゴリ・SKU・ASIN・TQ識別子。グループへの追加時と取込開始前に最新化する |
| 調査結果 | 調査日時、対象品番（有効な全品番）・調査時点のグループ所属・商品情報、SKUごとのBOSS・ECストック・フリー・Amazon在庫の数量、反映したSP-API取込結果。日付ごとに1件保持し、その日の初回のファイル取込またはAmazon取得成功時に作成し、同日の追加取込とAmazon取得成功時に更新する |
| 品番メモ・SKUメモ | 調査内の対象品番・SKUに紐づけ、入力内容の保存時に更新する |
| 取込ファイル | 元ファイル、種類・名前・アップロード日時と調査との紐づき。ダウンロードと期限削除に使用する |
| 在庫変動履歴の取込記録 | 元ファイル（30日で削除）、名前・期間・行数・確認の内容・取り込んだ利用者・アップロード日時。休日のBOSS在庫の補完を実行したときに作成する |
| 調査のBOSSの取得方式 | BOSSのレポートか在庫変動履歴からの再現か、再現した時点（9:00）と使った在庫変動履歴の取込記録。BOSSのレポートの取込と補完の実行時に更新する |

過去の調査は、調査時点の商品情報とファイル在庫の数量を使って表示する。その後に品番グループや有効な品番が変わったり、外部の商品マスタが更新されたりしても、過去結果のSKU・ファイル在庫・ブランド・カテゴリ・並び順は変わらない。新しい3ファイル調査のAmazon数量だけは同日取得成功時に更新され、旧5ファイル調査は保存済み数量を維持する。BOSS数量は、休日の補完と、補完した日のBOSSのレポートの取込で更新される。結果を開くために毎回外部APIへ接続する必要はない。

## 8. 構築時に調整する事項

本書で機能とデータの扱いを定め、次の細部は実装を進めながら調整する。

- 画面レイアウト、ボタン配置、SKUの並び順、検索の一致方式、メモの保存操作、Excelの見せ方。
- 開発言語・フレームワーク・データベースなどの構成、30日経過ファイルの自動削除の実装方法。
- 商品識別子管理システムのAPIのURL・認証方法・応答項目の対応。API連携を実装する際に、実際の仕様と接続情報を確認する。

これらのために詳細な確認事項一覧や運用設計書を別途作ることは前提としない。必要な機能を動かすための範囲で調整する。
