# Amazon在庫と在庫調査の統合改修計画

実装単位と依存関係は[統合改修チケット](Amazon在庫と在庫調査の統合改修チケット.md)にまとめる。

## 1. 背景と到達点

現行の3ファイル調査では、`survey_skus` のAmazon数量が0のまま保存され、調査表示時だけ `amazon_inventory_snapshots` の数量で置き換えている。一方、在庫推移の「モール全体」「総数」と日別CSVは調査側の値を参照するため、Amazon在庫が反映されない。調査時より前の最新取込を日付を問わず紐づけるため、前日のAmazon在庫が当日の調査に表示される可能性もある。

**改修後の原則:** Amazon取得履歴は取得の原本として保持し、調査がある日のSKU別在庫数は `survey_skus` を唯一の数量参照元とする。調査結果・在庫推移の合計・Excel・日別CSV・外部公開APIで同じ保存値を使う。

## 2. 日付と状態のルール

- 「その日」は `Asia/Tokyo` の暦日とする。調査は `surveys.executed_at`、Amazon取得は `amazon_inventory_imports.snapshot_date` で対応付ける。再照合は元調査の `executed_at` の日を使う。
- 同じ日に成功したAmazon取得が複数ある場合は、**最新の成功分**をその日のすべての3ファイル調査へ反映する。判定順は `basis_at` の降順、同時刻なら `completed_at`、さらに同時刻ならIDの降順とする。取得失敗・処理中のデータは使わず、失敗しても最後に成功した値を消さない。
- 当日の成功分がなければ、Amazon自社・FBAは `NULL` として「取込待ち」と表示する。前日以前の取得値を流用せず、0在庫と区別する。
- 当日の取得が成功したら、SKUコードが一致するスナップショットのAmazon自社・FBA数量を `survey_skus` に保存する。スナップショットに存在しないSKUは `NULL` のままとし、「未取得／対象外」と表示する。正常なスナップショット内の0は0在庫として保存する。
- 旧5ファイル調査のAmazon数量は保存済みの値を維持し、後から取得したSP-API在庫で上書きしない。
- 合算値は同日の調査に確定したSKU別数量から計算する。Amazonが取込待ち、または対象SKUのAmazon値が未取得なら、そのSKUの「モール全体」「総数」は `NULL` とし、部分的な合計を0在庫として表示しない。BOSS・フリー・ECストックの単独値は表示できる。
- Amazonと他倉庫の取得時刻は異なる。合算値は「同じ暦日の集計値」として表示し、Amazonの取得基準日時と調査日時を併記する。単一時刻の在庫と誤認させない。

| 調査の種類・状態 | `survey_skus` のAmazon数量 | 画面の状態 | 合算値 |
| --- | --- | --- | --- |
| 旧5ファイル調査 | 従来の保存値 | 取込済み（旧ファイル） | 従来どおり |
| 3ファイル調査、当日取得前 | `NULL` | 取込待ち | 未確定 |
| 3ファイル調査、当日取得成功 | 最新成功分の数量 | 取込済み・Amazon基準日時 | 全区分が揃うSKUで表示 |
| 3ファイル調査、取得成功だがSKU未収録 | 当該SKUのみ `NULL` | 当該SKUは未取得／対象外 | 当該SKUは未確定 |

## 3. データ構造

1. `survey_skus.amazon_own_stock` と `amazon_fba_stock` を `NULL` 許容に変更する。新しい3ファイル調査では、当日のAmazon取得がまだなければ `NULL` で作成する。旧調査の数値は変更しない。
2. `surveys` に調査のAmazon取得方式を明示する列（例: `amazon_source = legacy_file | sp_api`）を追加する。現行の `includes_amazon_inventory` は移行期間中だけ互換用に維持し、移行完了後に廃止する。
3. 既存の `surveys.amazon_inventory_import_id` は、その調査へ**実際に反映した**同日・最新成功取込のIDとして使う。`sp_api` 調査でIDがない場合は取込待ちを表す。取得基準日時はこの取込のメタデータから表示する。
4. `amazon_inventory_imports` と `amazon_inventory_snapshots` は取得原本・再適用の入力として維持する。通常の調査結果と合計の読取り時には、スナップショットとSKUを結合して数量を合成しない。

## 4. 書込みと再同期

### 3ファイル調査・再照合

1. BOSS・ECストック・フリー在庫を検証し、調査と全SKUを保存する。この時点でAmazon数量は `NULL` とする。
2. 調査日の最新成功Amazon取込があれば、同じSKUコードの数量を `survey_skus` にコピーし、調査の適用済み取込IDを設定する。旧5ファイル調査は対象に含めない。取得済みの場合は取込調査の応答前に数量を確定させる。
3. コミット後にも当日の再同期を行い、調査保存とAmazon取得成功が同時期に起きた場合の取りこぼしを防ぐ。再照合した調査も元調査の日付で同期する。

### Amazon取得成功時

1. 両方のSP-API取得と数量検証が成功し、スナップショットの保存が完了した時だけ成功とする。
2. 成功した取得日の3ファイル調査をすべて再同期する。既存のAmazon数量と適用済み取込IDを同じDBトランザクションで更新する。対象日以外と旧5ファイル調査は変更しない。
3. 再同期は冪等にし、必ず「その日の最新成功分」を選び直す。対象調査をロックしてから適用することで、同日の取得・調査が重なっても古い値が新しい値を上書きしないようにする。
4. 取込成功後の再同期に失敗した場合はエラーを記録し、同じ処理を再実行できるコマンドを用意する。既存のLaravel Schedulerから未反映の当日分を再試行する。ジョブが途中で停止しても修復できるようにする。

この日別再同期は1サービスにまとめ、手動取得・定期取得・調査実行・再照合・既存データの移行で同じ処理を使う。

## 5. 読取り経路と画面

- `SurveyResource` と `SurveyExcelExporter` の読取り時スナップショット合成を削除し、`survey_skus` のAmazon数量を返す。調査履歴一覧と結果画面には「取込待ち／取込済み／一部SKU未取得」とAmazon基準日時を表示する。取込成功後、開いている画面・次回表示時に調査データを再取得する。
- `InventoryTrendController` は、調査がある日はAmazon・BOSS・モール全体・総数を同じ調査の `survey_skus` から算出する。Amazonのみ取得され調査がない日は、Amazon単独の推移に限り取得原本を表示し、モール全体・総数は表示しない。取得元とAmazon基準日時はメタデータとして示す。
- 品番別の推移グラフは、対象日のSKUに未取得値があれば部分合計を出さず「取込待ち／未確定」とする。SKU別推移でも `NULL` を0として描画しない。
- `InventoryTrendCsvExporter`、`/api/v1/inventory/daily`、Excelは調査がある品番・日付では `survey_skus` の数量を使用する。調査がない品番・日付では、日別CSVと外部APIに最新成功Amazon取込のSKU別Amazon数量だけを返し、他の在庫区分は空欄またはJSON `null` とする。取込待ち・未取得のAmazon数量も空欄またはJSON `null` とし、取得後は同じ日付の再取得で数値を返す。外部API仕様書に値が後から確定・更新されることを記載する。
- 取込画面は3ファイルのままとし、Amazon取得の進行・成功・失敗を表示する。調査実行をAmazon取得待ちで止めない。

## 6. 既存データの移行

1. 適用前に調査件数、旧5ファイル調査と3ファイル調査の判定、Amazon取得日別の成功件数、曖昧な履歴を読取り専用で集計し、バックアップを取る。Amazonファイルの保存期限切れがあり得るため、フラグ・適用済み取込ID・保存済み数量・残存ファイルを組み合わせて分類する。判定不能な履歴は自動で上書きせず一覧化する。
2. スキーマ変更後、3ファイル調査のAmazon数量0（旧実装の仮値）を `NULL` にし、同日の成功取得がある日だけ再同期する。前日以前に紐づいていた取込IDは同日判定で置き換えるか、当日分がなければ解除する。旧5ファイル調査は触れない。
3. バックフィルはバッチ処理・再実行可能なコマンドにし、dry-runで対象件数を確認してから本番適用する。調査日・SKU・適用済み取込ID・数量を抽出して適用前後で照合する。
4. 本番ではアプリとマイグレーションを対応する組で配置し、スキーマ適用、バックフィル、キューとScheduler確認、画面確認の順に進める。移行中に取込を実行させないよう短時間のメンテナンス状態を設ける。

## 7. 検証と完了条件

- Amazon取得→調査、調査→Amazon取得の両順序で、同日の `survey_skus` に同じ値が入る。
- 同日に複数回成功した場合、全3ファイル調査が最新成功分へ更新される。失敗・再試行は確定済みの値を消さない。
- 日付が違う取得値を流用しない。日本時間の日付境界と、再照合の元日付を確認する。
- ASIN未設定・対象外SKUは0で埋めずに未取得と表示する。旧5ファイル調査の値・メモ・ファイルは維持する。
- 調査結果、履歴一覧、Excel、在庫推移のAmazon・モール全体・総数、日別CSV、外部APIの値が一致する。取込待ちはどの経路でも0や部分合計にならない。
- 同時実行と再同期の再試行でも、古い取込結果で上書きされない。PHPUnitの機能テストとVueの表示テストに加え、MySQLで移行・並行処理を確認する。
- 本番データの移行前後に、旧調査のAmazon数量一致、3ファイル調査の待機・確定件数、日別合計のサンプル照合を行う。

## 8. 実施順

1. 仕様と既存データの判定ルールを確定し、移行前監査とdry-runを用意する。
2. スキーマ変更と日別再同期サービス、調査・Amazon取得双方の書込み処理を実装する。
3. 調査API・Excel・在庫推移・CSV・外部APIを `survey_skus` 基準に統一する。
4. 履歴・取込・推移画面の待機表示と再取得を実装し、要件定義書・外部API仕様書・運用手順を更新する。
5. 自動テスト、MySQL移行検証、既存データのバックフィル、本番での調査順序別確認を行う。
